# FakaBridge 可选插件设计

基线 `4b098c8ff415b53dabb32758730cfb792b60cc9c`。设计草案，源于本轮后端架构评审后的需求补充。

## 目标

其他站点可以部署完整的通用商城，无须安装 FakaBridge、提供 Xboard 配置、运行对应 worker 或交付专属前端代码。采用 FakaBridge 的站点可以在运行期间加载已部署并完成校验的插件、接单、暂停接单、恢复。历史业务处理完成后，可以在运行期间注销插件。

启停面向一个部署。进行中的订单继续履约，已出售订阅所承诺的售后和权益保持可用。插件与核心的版本升级按正常交付流程进行。

## 当前基线

- 后端启动时静态导入并注册 `xboardFulfillmentProvider`，应用固定挂载 FakaBridge 路由，并在 `/api` 上安装 FakaBridge 运行配置中间件。前端购买扩展也静态导入 Xboard hook。
- 当前后台启停可以关闭新履约并保留历史任务。这个行为适合直接作为未来“暂停接单”的语义。
- 订单取消、争议和售后，以及商品可售性、套餐导入与重绑仍直接使用 FakaBridge 的任务表、专属字段或协议。

源码可核对 [插件注册](https://github.com/amo0114/MoNexus/blob/4b098c8ff415b53dabb32758730cfb792b60cc9c/server/src/bootstrap/extensions.ts#L4)、[路由挂载](https://github.com/amo0114/MoNexus/blob/4b098c8ff415b53dabb32758730cfb792b60cc9c/server/src/app.ts#L177)、[订单取消](https://github.com/amo0114/MoNexus/blob/4b098c8ff415b53dabb32758730cfb792b60cc9c/server/src/modules/orders/cancellation.ts#L24)、[前端注册](https://github.com/amo0114/MoNexus/blob/4b098c8ff415b53dabb32758730cfb792b60cc9c/src/extensions/registry.ts#L3)和[运行配置手册](https://github.com/amo0114/MoNexus/blob/4b098c8ff415b53dabb32758730cfb792b60cc9c/docs/operations/runtime-settings.md#L118)。

## 职责和依赖

| 归属 | 负责的能力 |
| --- | --- |
| 商城核心 | 订单状态、支付、积分、库存、结算、授权、幂等、历史订单及交付读取 |
| 核心履约接口 | 按已冻结的供应商标识找到订单的履约事实与取消评估；供应商缺失时给出明确的不可处理状态 |
| FakaBridge 插件 | Xboard 协议与版本、容量/SKU 映射、目录同步、邮箱证明、账号绑定、流量重置、任务和撤销、自有管理及购买界面 |
| 插件装载入口 | 从部署制品中发现批准的插件，校验版本与依赖，注册能力、路由和后台任务，应用部署级启停状态 |

复用 `FulfillmentProvider`。只为当前确有需要的商品可售性、订单履约事实和专属 UI 补接口。商品选择执行器仍由服务端根据规格绑定决定。订单用持久化的中立标识识别历史履约归属，即使插件缺失也能区分外部订单与可人工处理的本地订单。旧 Xboard 请求字段留在兼容入口，按原有语义转换并保留幂等计算结果。

核心保留固定的插件路由分发入口。插件注册、暂停和注销通过入口分发，新请求在进入处理器前按能力和授权检查。前端根据服务端可用能力决定是否显示入口，配置了插件的站点按需加载独立页面和扩展组件。现有部署保留原有路由和已启用配置的兼容入口。

## 运行时状态

| 状态 | 新业务 | 历史业务 |
| --- | --- | --- |
| 未安装 | 普通商城完整可用，插件入口不可用 | 通用订单详情、交付与审计可读。遇到未能判断的外部状态交给人工处理 |
| 已安装，尚未启用 | 可配置并做只读校验，待 worker 和配置就绪 | 存在遗留记录时按原版本恢复历史处理 |
| 已启用 | 允许新建插件关联业务 | 按原渠道、实例、任务和配置版本处理 |
| 已暂停接单 | 停止新购买、新续费和新运营开通 | 已受理任务及约定内的退款、撤销、对账和已有订阅服务继续 |
| 可卸载 | 新业务入口仍关闭，运营可执行注销 | 待处理和未知任务、活动租约、待撤销、争议及仍依赖插件的有效售后或权益均已解决或有确认的接管方案 |

暂停的最终检查在下单事务内完成，与配置变更按确定顺序互斥。暂停提交后发起的新业务在扣款和建任务前被拒绝。已经提交的订单继续按原版本运行。状态跨实例共享，API 与 worker 使用同一启停状态。重复启停幂等。卸载先停止接单并核对历史义务，再停止并等待在途操作、注销入口。注销失败保持暂停接单与历史处理能力。记录控制操作、尚未完成的卸载条件和失败原因。

## 实施次序

1. **先切断核心直接依赖。** 给订单读写路径提供通用的履约归属和状态读取，保留 FakaBridge 专属表、任务标识、原配置版本与启停行为。建立 core 侧禁止直接导入具体实现的静态门禁，并检查绕过 import 的专属任务表访问。
2. **再实现运行时装载和独立交付。** 把 FakaBridge、目录、后台和 UI 入口移到可选制品，核心可独立构建和运行。插件的必要迁移由受控的部署流程先准备好，核心运行时校验 schema 和契约版本后再装载。从旧版本升级时，先补齐历史履约归属和兼容读取，随后才开放注销能力。扩展存储仍需遵守订单先锁、任务后锁，与任务创建和结果应用相关的本地写入沿用现有事务，远端操作在事务外执行。

第一阶段保留插件表是迁移安排。验收独立交付时，新核心部署应当能在单独的空库中运行，无须安装插件迁移。历史站点保留账务、退款、审计、任务幂等记录及需要保留的原目标证据。升级应允许回滚到仍能识别旧任务的版本。

## 验收

1. **核心独立。** 用缺少插件制品、配置和插件迁移的环境构建并启动，走通普通商品的发布、下单、交付、退款。Xboard 入口不展示，且核心不加载插件代码或后台任务。
2. **无重启接入与启停。** 运行中装载已准备好的制品，在同一进程中启用、暂停和恢复。两实例分别承担 API 和 worker 时，暂停后双方按同一状态行事，竞态下无新增扣款、重复入账或孤立任务。
3. **历史不漂移。** 暂停后旧任务仍以原供应商、协议、目标、操作键和配置版本处理。未确认的远端结果保持可追踪，原有退款与撤销条件保持生效。
4. **卸载有证据。** 活动租约、未决退款、未知任务或仍依赖插件的有效服务与权益阻止注销。正常卸载后，请求和后台任务停止，旧订单及交付仍能读取。重新载入同一插件时，可按保留的原始标识恢复必要的历史操作。

验证从 `npm run test:architecture` 与 `npm run check:architecture` 开始，并使用两套隔离数据库分别验证全新核心部署和现有部署升级。关联回归包括 `order-cancellation-bridge.test.ts`、`fulfillment-job-engine.test.ts`、`admin-faka-runtime.test.ts`、`runtime-settings-multi-process.test.ts`、结账幂等与前端插件入口可见性。本轮到设计草案为止。
