## 1. 目标与边界

为商品详情页的“相关推荐”建立一套可信的基础统计：卡片真正被看到多少次、被点了多少次、点击后有多少兑换，并能按匹配等级、同店/跨店、位置比较。

范围内：

- 只覆盖 `GET /api/products/:id/recommendations` 返回、在详情页三种布局展示的推荐卡片。
- 沿用现有推荐架构（同分类、模板与关键值匹配、同店优先、最多 6 件、可售过滤），**不新增个性化、学习排序或广告计费**。
- PR3（名称建议）、PR4（弱匹配准入调整）保持暂不调整。本方案的数据用于将来复审，不触发规则变化。

不在本轮：

- 首页、商城列表、推广位、聊天机器人等其他入口的曝光统计。
- A/B 实验分流、增量收益（lift）评估、按曝光或点击计费。
- 给商家看的推荐报表（先只做平台管理员视角）。

## 3. 事件契约

### 3.1 推荐清单凭证（服务端真实元数据）

匹配等级、位置和同店关系必须来自服务端，前端不能自行推断或填写。同时，推荐接口是读接口，不应为了统计在每次读取时写库。方案如下：

- 推荐响应增加一个字段 `tracking`，统计关闭时不返回：

  ```ts
  type RecommendationsResponse = {
    productId: number
    items: RecommendationItem[]          // 现有字段不变
    tracking?: { listToken: string }     // 统计开启时才有
  }
  ```

- `listToken` 是服务端签发的不透明凭证：`base64url(payload) + "." + HMAC-SHA256(payload)`。payload 包含：

  | 字段 | 说明 |
  | --- | --- |
  | `v` | 凭证版本，固定 1 |
  | `listId` | 本次返回清单的随机 UUID |
  | `src` | 来源商品 ID（详情页商品） |
  | `sv` | 推荐策略版本，首版 `pdp-rec-v1`；推荐规则改变时递增 |
  | `aud` | `guest` / `member`（服务端身份推导） |
  | `iat` | 签发时间（秒） |
  | `items` | 按展示顺序的 `[{ id, pos, tier, same }]`，`pos` 为 1..6，`tier` 为 1..3，`same` 为是否同店（含平台自营同桶） |

- `tier` 和 `same` 取自候选 SQL 已算出的结果（PR #253 新增的 `queryRecommendationCandidates` 返回的分数），不重新计算。
- 签名密钥使用新增环境变量 `RECOMMENDATION_EVENT_HMAC_KEY`：规范 base64、恰好 32 字节，必须独立于 `JWT_SECRET`、`MFA_ENCRYPTION_KEY`、`ABUSE_HASH_KEY`、`ALTCHA_HMAC_KEY`（与 `ALTCHA_HMAC_KEY` 的校验方式一致）。未配置时不签发凭证，整个统计功能关闭。
- 凭证有效期 2 小时；超过有效期的事件直接丢弃（返回 204，不报错）。
- 凭证不含用户 ID、商品名或任何秘密；即使被解码，也只暴露公开商品 ID 与粗粒度匹配等级。

### 3.2 曝光（impression）

**计数条件**（全部满足才计一次）：

1. 卡片面积至少 50% 位于视口内；
2. 连续可见满 1 秒；
3. 页面处于前台（`document.visibilityState === 'visible'`）。切到后台时计时清零，回到前台重新计时；
4. 推荐清单已经渲染为真实卡片。加载骨架、空结果、请求失败、开发预览都不计。

**重复曝光规则**：

| 情形 | 是否新增曝光 |
| --- | --- |
| 同一清单中的同一卡片滚出视口后再滚回 | 否，每个清单的每个推荐商品最多 1 次 |
| 同一页面内切换套餐、打开弹窗、窗口尺寸或布局变化（手机/平板/桌面切换） | 否，清单不变 |
| 离开详情页后再进入同一商品（包括浏览器返回） | 是，重新请求推荐，产生新清单 |
| 登录、退出或切换账号后推荐重新请求 | 是，新清单 |
| 同一访客当天多次看到同一推荐 | 每次都计入“曝光次数”；报表另给“去重曝光”（访客 × 业务日 × 来源 × 目标 去重） |

实现约束：用 `IntersectionObserver`（`threshold: 0.5`）加 1 秒计时器；不轮询 `getBoundingClientRect`。同一清单的曝光在客户端攒批，满足“攒满 6 条、离开页面（`pagehide` / `visibilitychange` 变为 hidden）、或 5 秒”任一条件即发送，使用 `fetch(..., { keepalive: true })`。

### 3.3 点击（click）

**计数条件**：推荐卡片链接被激活，包括主键单击、回车、中键点击（`auxclick`），以及 Ctrl/⌘ 单击后台新标签打开。右键菜单中的“在新标签页打开”浏览器不暴露，**不计入**（已知漏计）。

**事件内容**（客户端只发这些，其余由服务端从凭证和数据库得出）：

```ts
type RecommendationEventBatch = {
  listToken: string
  visitorId: string                         // 复用流量模块的访客 UUID
  events: Array<{ type: 'impression' | 'click'; productId: number }>  // 1..12 条
}
```

服务端从凭证中按 `productId` 找到对应条目，得到位置、匹配等级、同店关系、来源商品和策略版本；`productId` 不在凭证清单里的事件丢弃。登录用户的 `userId` 由认证中间件推导，不接受客户端传入。

**重复与关联规则**：

- 每个清单的每个推荐商品最多 1 次有效点击，用于点击率。重复点击只按“最早一次”入库。
- 点击隐含曝光：入库点击时如果该商品还没有曝光记录，同时补一条曝光，并标记 `implied=true`。这样点击率不会超过 100%，也能统计“未满 1 秒即点击”的比例。
- 真实曝光可以更正隐含曝光：之后同一清单、同一商品的真实曝光到达时，只把 `implied` 改为 `false`；不新增记录，不改首次记录时间 `receivedAt`。真实曝光先到、点击后到时，不做任何更改。
- 点击在导航前发送（keepalive），不阻塞跳转；发送失败不提示用户，也不影响导航。

### 3.4 上报端点

`POST /api/recommendations/events`：

- 中间件与流量端点一致：`authenticateIfPresent`、`requireActiveUserIfPresent`、Zod 严格校验。
- 处理顺序：验签 → 检查有效期 → 校验 `productId` 属于凭证清单 → 写库（同一批次一次插入，唯一键冲突时忽略）。
- 凭证无效、过期或 `productId` 不匹配时返回 204 并丢弃，不暴露原因，也不计入错误告警；只用一个枚举标签的 Prometheus 计数器记录丢弃原因。
- 沿用全局 API 限流，不另设统计专用限流。客户端每个清单最多发送 12 条事件（6 次曝光 + 6 次点击）。

## 4. 兑换归因

| 规则 | 定义 |
| --- | --- |
| 可归因点击 | 点击时为登录用户（事件带 `userId`）。访客点击计入点击率，但**不参与兑换归因**（订单无法关联访客；方案不改下单接口） |
| 计入的订单 | 同一 `userId`，`Order.productId` 等于被点击的推荐商品（任一套餐都算），`createdAt` 晚于点击时间 |
| 主口径窗口 | 点击后 **24 小时**内创建的订单 |
| 参考口径 | 点击后 7 天内，只作为敏感性参考，不作为主指标 |
| 多次点击 | 末次点击归因：一笔订单只归给下单前最近一次**已记录的有效点击**（同一用户、同一商品、已入库的登录用户点击，且在窗口内）；未入库或被去重的点击不参与。一次点击可以带来多笔订单（例如同时买了多个套餐），每笔都是归因订单 |
| 订单状态 | **原始归因**计入所有状态的订单，包括后来退款的订单；**净归因**排除报表计算时已是 `refunded` 的订单。`pending`（已扣除或冻结积分）、`processing`、`delivered`、`closed`（验收完成）、`disputed` 都保留在净归因内。退款发生在报表计算之后时，以下次计算为准 |
| 金额 | 积分为整数，按 `Order.price` 求和，原始和净归因分别统计；不换算人民币 |
| 不归因 | 同一用户在窗口内购买的其他商品（无“光环”效应）；点击前已经存在的订单 |

报告必须说明：归因只说明“点击后发生了兑换”，不证明推荐带来了增量。没有对照组之前，不能把归因兑换当作推荐收益。

## 5. 指标与比较口径

### 5.1 基础指标

| 指标 | 定义 |
| --- | --- |
| 曝光次数 | 曝光记录数（含 `implied`），按曝光日归组 |
| 去重曝光 | 按 访客 × 业务日 × 来源商品 × 推荐商品 去重 |
| 点击次数 | 点击记录数（每个清单每个商品最多 1 次），按点击日归组，只作总量参考 |
| 点击率（CTR） | **已被点击的曝光记录数 ÷ 曝光记录数**。点击按 `(listId, productId)` 归到对应曝光，跟随该曝光的日期和分组；“23:59 曝光、次日 00:01 点击”计入前一天 |
| 转化点击数 | 至少带来一笔符合 24 小时归因条件、且非退款订单的可归因点击数 |
| 兑换转化率 | **转化点击数 ÷ 可归因点击数**（只算登录用户的点击），按点击日归组。一次点击买两单，算 1 次转化、2 笔归因订单 |
| 原始 / 净归因订单数 | 24 小时窗口内归因的订单数；原始含后来退款的订单，净排除 `refunded` |
| 原始 / 净归因积分 | 对应订单的 `price` 合计 |
| 千次曝光兑换 | 净归因订单数 ÷ 登录用户曝光记录数 × 1000，订单经点击归到对应曝光的日期和分组（订单数可以超过点击数，这个指标不是比率上限 100% 的转化率） |
| 推荐覆盖率 | 至少产生 1 次曝光的推荐清单数 ÷ 同期详情页 PV（取自现有流量统计；两个数据源存在漏计差异，只作趋势参考） |
| 平均可见件数 | 有曝光的清单，平均每个清单的曝光商品数 |
| 访客点击占比 | 访客点击 ÷ 全部点击。用于说明有多少点击无法归因 |

### 5.2 比较维度与规则

可分组维度：策略版本 `sv`、匹配等级 `tier`（3/2/1）、同店/跨店（平台自营单列）、位置 `pos`（1..6）、身份 `aud`、业务日。

日期口径（业务日均按 Asia/Shanghai）：

| 指标 | 归组日期 | 未成熟标记 |
| --- | --- | --- |
| 曝光次数、点击率 | 曝光的首次记录时间 | 曝光日结束后 2 小时内（凭证有效期内仍可能有点击到达） |
| 点击次数 | 点击记录时间 | 不需要 |
| 兑换转化率、归因订单与积分 | 点击记录时间 | 点击日结束后 24 小时内（归因窗口尚未结束） |
| 千次曝光兑换 | 曝光的首次记录时间 | 曝光日结束后 26 小时内（2 小时凭证有效期 + 24 小时归因窗口） |

“未成熟”的分组照常返回数字，但要标明窗口未结束、数字可能继续增加，不参与比较结论。

比较规则：

- **位置混杂**：同店商品总排在前面，直接比较“同店 vs 跨店”的点击率会被位置影响。默认报表按位置分层，比较同一位置上的不同类型；汇总值只作参考。
- **最小样本**：某个比较单元的曝光少于 1000 次或点击少于 30 次时，标注“样本不足”，不给结论。按当前生产目录规模（审计时仅 2 件范围商品），短期内大多数单元都会是样本不足，这属于正常结果。
- **策略版本**：不同 `sv` 的数据不合并比较；推荐规则（包括将来的 PR4）变化时必须递增 `sv`。
- **基线**：统计上线后、任何推荐规则调整之前，先积累至少 4 周或达到最小样本，作为 PR4 复审的前后对比基线。

## 6. 存储、保留与隐私

首版只新增两张原始事件表（迁移只新增，不改动已有表），不建汇总表或状态表：

| 表 | 关键字段 | 约束 |
| --- | --- | --- |
| `RecommendationImpression` | `listId`、`productId`、`sourceProductId`、`position`、`tier`、`sameSeller`、`strategyVersion`、`audience`、`visitorId`、`userId?`、`implied`、`receivedAt` | 唯一键 `(listId, productId)`；索引 `(receivedAt)`、`(sourceProductId, receivedAt)` |
| `RecommendationClick` | 同上（无 `implied`） | 唯一键 `(listId, productId)`；索引 `(userId, productId, receivedAt)` 供归因关联 |

- 时间以服务端 `receivedAt` 为准，不信任客户端时钟。
- 原始事件保留 90 天，和流量统计一致，由 cron（经 `cronLease`）删除过期数据。
- 报表直接查询原始记录并缓存 30 秒；cron 只负责过期清理。当日曝光量超过约 50 万条、或报表查询超过 2 秒时，再按流量模块的做法增加日汇总表；**首版不预建汇总表**。
- 不存商品名、IP、User-Agent、页面 URL 或任何购买资料。`userId` 只用于归因关联；报表只输出聚合数字和商品 ID/名称（名称在查询时关联）。
- 买家可见的页面与接口不出现任何统计字段（`tracking.listToken` 除外，它不含个人信息）。

## 7. 开关、上线与报表

- **开关**：只有配置了 `RECOMMENDATION_EVENT_HMAC_KEY` 时才签发凭证；客户端只在生产构建、且响应带 `tracking` 时上报（与 `usePageView` 一致）。去掉密钥即可关闭，无需回滚代码。
- **配置**：新环境变量加入 `server/src/config/index.ts` 和 `.env.example`；生产启用前由运维生成独立随机密钥。
- **报表**：首版提供管理员接口 `GET /api/admin/reports/recommendations?range=7d|30d|90d&groupBy=tier|seller|position`，返回 §5 的指标与样本不足标记。后台页面另行排期，本方案不包含前端报表页。
- **失败影响**：统计请求失败、凭证缺失或密钥未配置时，推荐展示、导航和购买都不受影响。

## 9. 已确认的决定

以下五项已由 Owner 于 2026-10-14 确认：

1. **归因窗口**：主口径 24 小时、参考口径 7 天。
2. **访客点击不归因**：不为统计改动下单接口。代价是访客先点击、登录后再购买的情况会漏计（报表用“访客点击占比”提示漏计规模）。
3. **独立签名密钥** `RECOMMENDATION_EVENT_HMAC_KEY`，缺失时统计关闭。替代方案是每次读推荐时写一条“已返回清单”记录，会让读接口产生写库副作用，不采用。
4. **报表先做管理员接口**，不做后台页面和商家视角。
5. **曝光门槛**采用 50% 面积 + 连续 1 秒（常用的展示广告可见性标准）。
