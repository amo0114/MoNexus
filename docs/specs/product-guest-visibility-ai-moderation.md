# 分类游客可见性与人工公开准入实施方案

文档 ID：SPEC-CATALOG-VIS-001；版本：0.2；日期：2026-10-21。

状态：修订设计，尚未实施。取代 0.1 中“首版建设完整 AI 自动审核与私有媒体系统”的建议。本文中的触发线和工作拆分是建议决策，尚无模型实测结果。

## 1. 本次拍板

接受“P1 分类限制 → P1.5 人工公开准入 → 达到触发线后评估 AI”的拆分。P1 可独立交付；本项目推荐在 P1 后接续交付 P1.5，以解决商家故意错分类的问题。

机器人采用“未绑定用户按游客，绑定有效站内账号后按登录用户”的规则。这是明确的产品行为变化，以独立 PR 和客户端联调交付，不能藏在分类过滤的重构中。不能把全部机器人用户一律改成游客，也不能继续让未绑定用户无条件使用 member 视角。

首版不建设 AI 工作器、持久任务、租约、熔断、预算预留、配置 epoch、影子/强制模式、视觉检测、私有媒体代理、历史图片迁移、定期复评或审核申诉系统。

**当前的投入对象是有限的游客公开申请，不是全部商品，也不是全部商品编辑。**

### 2.3 本期保护目标

游客通过网站、商品 API 和未绑定的机器人请求，不能获得受限分类及商品的名称、说明、价格、套餐、评价、分类元数据和图片 URL。

本期不承诺“已知图片 URL 无法直接访问”，不承诺撤回浏览器、搜索引擎或第三方已保存的内容，也不把登录限制描述为禁止注册账号后查看。

## 3. P1：分类游客可见性

### 3.1 数据和管理入口

ProductCategory 新增 guestVisibility，仅有 public / members_only 两值，默认 public。保持 Product.visibility 原有默认值和现有商家选择。

管理员在现有分类创建、编辑表单设置该属性，分类列表显示标签；沿用现有管理员鉴权、MFA、输入校验、并发约定和 AdminLog。商家只能选择分类，不能改分类权限。

受限分类的名称、描述、图标、封面及 legacy productTypes 投影均不返回游客。分类限制变更对该分类已有商品立即生效，不等待商品重存或人工复核。

当前分类是平级、商品单分类，本期不增加分类树或多分类。未来若引入，则执行“祖先任一受限”和“关联分类任一受限”的最严规则。

### 3.2 统一判定

保留现有商品/商家生命周期规则。对有效登录用户继续使用原有访问规则；对游客额外要求 Product.visibility=public 且分类 guestVisibility=public。

分类或必需访问字段缺失时不默认为公开。商品不存在、归档、非可公开状态及商家异常仍保持原有不可用行为，不把这些情况统称为“请登录”。

受限商品直接访问详情、评价等入口时，复用 403 PRODUCT_LOGIN_REQUIRED 和“登录后查看商品”。错误体不包含商品名称、分类、图片、价格或其他详情。

### 3.3 四条路径及等价性

统一扩展 products/visibility.ts 的四类表达：publicVisibilityWhere、guestVisibilitySql、assertPublicProductAccess、isCurrentlyPubliclyVisible。

同一组商品、分类、商家、生命周期和 audience 样例同时喂给四条路径。Prisma 查询结果、SQL 查询结果、内存判断和详情断言必须一致，避免仅列表生效、推荐漏放。

新增访问快照字段应在类型上要求加载；不能用 optional 字段的“缺省公开”兼容旧调用方。缺字段的测试应失败，而不是静默跳过分类检查。

### 3.4 入口与缓存

| 入口 | P1 处理 |
| --- | --- |
| 商品列表、搜索、分类筛选 | 查询阶段过滤，缓存命中后实时复核 |
| 详情、评价、相关推荐 | 源商品先鉴权，候选商品逐批过滤 |
| 商家店铺商品与分类聚合 | 复用统一访问规则；汇总不得暴露受限商品 |
| 推广、精选、榜单卡片 | 数据查询与缓存命中均过滤；不修改排名计算语义 |
| 分类 registry、兼容 productTypes | 解析可选有效身份，按 audience 输出 |
| 分享创建、已存在分享链接的落地页 | 仍执行当前访问检查，受限商品无公开预览详情 |
| 机器人商品查询 | 按第 5 节明确的绑定规则处理 |

商品相关 JSON 初期采用 Cache-Control: private, no-store；服务端内部 Redis 缓存仍可使用，但键必须区分 guest/member，缓存不是权限真相源。no-store 不撤销此前已缓存的响应。

分类收紧后即使 Redis 失效通知失败，返回前的数据库访问复核也必须拒绝。数据库无法确认权限时不得用旧缓存回退为公开。

旧缓存 DTO 与当前商品内容版本不匹配时重建或剔除，不能用新权限授权旧文案。推广等独立投影缓存同样检查。

### 3.5 前端状态切换

src/api/registry.ts 当前只有单份缓存和在途 Promise。改为按 audience 和登录代数隔离；登录、退出、账号切换、鉴权失效时清理分类、商品与推荐缓存。

旧在途请求不得在退出或换账号后回填受限数据。退出后清空当前受限详情；页面激活、后退/BFCache 恢复时检查当前身份代数。

游客 UI 不保留受限商品的占位卡片、图片预加载链接或商品数量提示。登录后重新请求，复用现有详情登录提示。

## 4. P1.5：人工公开准入

### 4.1 为什么推荐实施

仅靠分类不能防商家选错类。当前生产规模很小，人工确认少量 public 申请比新建 AI 基础设施更便宜、更容易解释，也更严格。

只审核“申请向游客公开的商品”和“已公开商品的审核内容修改”。members_only 商品无需申请或等待人工批准，可继续正常编辑、发布和面向登录用户销售。

P1 本身可以上线，但必须说明它不防故意错分类；只有 P1.5 及机器人配套生效后，才能宣称当前站点和机器人匿名查询都执行公开准入。

### 4.2 最终门禁

游客可见 = 现有生命周期允许公开 + 商品 public + 分类 public + 当前公开内容版本获管理员批准。

审批不修改 Product.visibility、分类、商品上架状态或订单权限。人工批准不能覆盖受限分类和商品自身 members_only。

管理员自己的平台商品也不默认免审，可由有权限的管理员直接执行明确的批准动作并审计，不暗中自动创建通过记录。

### 4.3 最小数据模型

| 对象 | 字段建议 | 用途 |
| --- | --- | --- |
| Product | publicContentRevision，初始 1 | 公开审核内容的专用版本 |
| ProductGuestEligibility | productId 唯一 | 每商品一条当前公开准入记录 |
| 准入记录 | decision：pending / approved / denied | 当前人工结论；撤销写为 denied + reasonCode=revoked，不新增状态值 |
| 准入记录 | reviewedRevision | 批准或拒绝对应的内容版本 |
| 准入记录 | version | 审批操作自身 CAS，防同版本操作互相覆盖 |
| 准入记录 | reviewedBy、reviewedAt、reasonCode | 人工来源和有限原因码 |
| 现有 AdminLog | 审批/拒绝/撤销及版本 | 复用审计，不新建审批引擎 |

无记录、pending、denied 或 reviewedRevision 与当前商品不一致，一律不向游客展示。保留原 contentVersion；它的变化范围与公开审核不同，不直接拿它使所有价格修改失效。

首版不增评估历史表、任务表、模型字段、人工到期时间、decisionEpoch 或单独申诉表。确有需要时再扩展；同一商品当前申请可以再次审核，无需通用工作流。

### 4.4 哪些变化使批准失效

商品名称、摘要、富文本可见内容、details 展示说明、对外展示属性、分类选择、封面/图片引用、套餐名称/说明，以及新增或启用未审核套餐，都必须更新 publicContentRevision，并使原批准失效。

纯价格、库存、销量、评分聚合和内部备注不在审核内容中，不触发重新审核。价格仍走原有交易校验；用户评价本身不在本次商品准入审核范围中，其游客读取仍先检查商品权限。

商家、管理员、上游同步、旧版兼容接口的展示写入都必须覆盖；不能只改新编辑器。

Product.visibility 的任何变化（public ↔ members_only）同样递增 publicContentRevision，并把准入记录重置为 pending，与第一段列出的展示字段同等对待。因此转为 members_only 时旧批准立即失效；再次选择 public 时，对应的是新版本，必须重新批准，来回切换不能让旧批准复活。待审核列表只查询 visibility=public 的商品，members_only 商品的 pending 记录不会出现在待办中。

分类权限收紧直接拦截，不需要给整类商品批量递增版本。分类放开不会创建批准；已有批准能否沿用仅看内容版本和明确撤销状态，不能覆盖当前分类规则。

### 4.5 事务与 CAS

展示内容写入、公开版本递增和准入记录 pending 重置，在同一 PG 事务内完成，沿用商品行锁。套餐展示内容更新同样锁对应商品，并遵守统一锁顺序。

管理员打开审批时读取商品当前公开内容预览及 publicContentRevision、eligibility.version；提交批准/拒绝必须携带这两个 expected 值。

提交时重读并比较，任何变化返回 409，要求刷新。两个管理员同时操作也使用 eligibility.version 排序；已被撤销的审批不能被晚到旧批准覆盖。审核事务不包含外部服务调用。

不建立异步任务：待审核列表直接查询 public 商品中无有效批准的记录；一商品最多一条当前申请，不因重复保存生成多条待办。

#### 4.5.1 状态流转

| 当前状态 | 触发 | 结果 |
| --- | --- | --- |
| 无记录 | 商品首次以 public 保存 | 创建 pending，reviewedRevision 为空 |
| pending | 管理员批准（expected 值匹配） | approved，reviewedRevision = 当前 publicContentRevision |
| pending | 管理员拒绝 | denied，reviewedRevision = 当前版本，附 reasonCode |
| approved | 管理员撤销 | denied，reasonCode=revoked；游客立即不可见 |
| 任意状态 | 展示字段或 visibility 变化（§4.4） | pending，reviewedRevision 保持原值，此时与当前版本不一致 |
| denied | 商家未修改任何内容 | 保持 denied，不能直接重新申请 |

商家在被拒绝或被撤销后要再次申请，只能修改展示内容，或者把 visibility 切走再切回 public。这两种操作都会递增版本，重新进入 pending。首版不建申诉表，也不单独设频率限制：每件商品只有一条当前记录，重复提交不会增加待办数量；需要限流时，沿用现有 API 限流即可。

商家界面根据 decision 和 reasonCode 显示固定文案："待公开审核""未获批准，修改内容后可重新提交""公开资格已被撤销"。

### 4.6 UI 和接口

商家商品列表显示“仅登录可见、待公开审核、游客可见、未获批准”及固定原因文案。选择 public 时提示“保存后需管理员确认才能向游客展示”，保存成功不等于公开成功。

管理员复用现有商品管理，增加待公开审核筛选、公开内容预览、批准、拒绝和撤销操作。不新建独立运营控制台、申诉中心或抽检平台。

写接口要求现有 active admin + 当前 MFA，附 expectedPublicContentRevision 和 expectedEligibilityVersion。商家接口拒绝任何提交 decision、reviewedBy 或 reviewedRevision 的尝试。

可选接口草案：POST /api/admin/products/:id/guest-eligibility，body 为 action、expectedPublicContentRevision、expectedEligibilityVersion、reasonCode。创建首条记录也需在商品锁内比较，避免并发首次批准。

## 5. 机器人产品变更：未绑定 guest，绑定后 member

### 5.1 明确行为

| 请求身份 | 商品视角 | 返回行为 |
| --- | --- | --- |
| 未提供平台身份或未绑定 | guest | 只搜索游客可见商品，提供绑定引导 |
| 已绑定有效站内账号 | member | 保持原有登录用户商品覆盖 |
| 绑定账号已停用/删除/受限 | 不授予 member | 返回固定账号不可用提示，不继续读受限商品 |
| 绑定查询失败 | 故障 | 不默认为 member，不将错误当“未找到商品” |

原有代码注释说明希望为已绑定用户提供 member 搜索，但当前商品路由没有据此核验绑定。这是意图和实际实现不一致，不应据旧注释直接推断当前请求均已绑定。

### 5.2 身份来源

沿用现有机器人 HMAC 签名和平台绑定机制；从签名保护的 platform、platformId 查询 ChatBinding，再校验用户状态。不能信任请求体里的 userId 或 audience。

HMAC 证明来自受信机器人服务，机器人服务还必须保证 platformId 取自实际消息发送者，不能让用户通过命令参数冒充他人。每次查询核验绑定，解绑或账号失效后立即失去 member 权限。

### 5.3 不让空结果变成错误体验

未绑定用户查询无结果时，文案应为“当前没有可公开展示的匹配商品，绑定账号后可查看登录用户商品”，而不是“平台没有商品”。

公开商品存在时正常返回这些商品，同时允许展示通用绑定入口。不能透露受限商品数量、名称或“还有几件商品未展示”。

直接查询受限商品，返回固定“绑定账号后查看”状态，无商品详情。绑定后重新搜索；旧 guest 游标不能继续 member 查询，反之亦然。

若聊天命令在群内执行，member 内容只能通过私聊或该账号专属回复交付。无法保证接收范围的群回复保持 guest；不能把“请求者已绑定”变成向整个群公开受限商品的理由。这一项须由机器人客户端联调验证，缺少私有回复能力时先提供私聊/站内查看引导。

### 5.4 发布条件

独立 BOT PR，更新接口契约、机器人调用方、文案、游标测试和绑定/解绑回归。客户端暂时不能提供可信发送者身份或私有回复时，保持 guest 并提示绑定/私聊，不静默改为 member 兼容。

P1 的分类功能可先发布，但“所有匿名入口均隐藏”这一整体验收必须包含 BOT 变更。若 BOT 未完成，需要明确暂时限制相关机器人商品命令，不能保留可泄露路径后仍宣称完整达标。

## 6. 首版图片边界与共享资产

### 6.1 接受缩小范围

常规上传在 storage/types.ts 使用 hashKey(buffer)，以图片字节的 SHA-256 截断值及扩展名形成 key；相同字节会得到相同 key。首版不再为常规上传重复建设“不可变对象版本”系统。

保留现有图片 URL、浏览器缓存、普通 img、懒加载和分享预览机制；受限商品的分享预览不含商品详情或图片。商品相关 JSON 使用 no-store，不将通用图片全部改成 no-store。

不引入鉴权 Blob 获取、私有代理、签名链接、对象搬迁或历史 CDN 清理。

### 6.2 准确表述剩余风险

内容哈希降低猜测空间，但不是访问控制。已知 URL 仍可被分享；拥有相同字节的其他人也可能推导 key，而不一定是此前访问过该商品的人。因此本期承诺的是“响应不分发受限商品图片 URL”，不是“源图片不可被匿名读取”。

no-store 只约束后续符合该响应指令的缓存，不撤回旧页面、浏览器缓存或第三方内容。若这些风险超出平台可接受范围，再独立设计私有媒体，而非在本期宣称已经解决。

### 6.3 共享图片

同一 key 可能被多个商品、分类封面或其他模块引用。不能因一个商品被限制而直接删除或迁移该 key，导致其他商品图片损坏。

本期检查共享引用只用于防误删、说明影响和人工公开审核，不新建全站媒体权限图。一个已批准公开商品合法使用相同图片时，该图片继续公开；这不能作为受限商品 DTO 可返回的理由。

仅当实际出现图片直链传播敏感内容、合同要求资源鉴权或威胁模型变化时，重新评估共享引用、存储策略和私有交付方案。

## 8. 验收与测试

### 8.1 P1 功能验收

分类 public/members_only × 商品 public/members_only × guest/member × 生命周期状态的组合一致。四条访问表达执行同一批样例，特别覆盖缺失关联与错误访问快照。

覆盖列表、搜索、详情、评价、推荐、店铺、推广、精选、榜单、registry 和分享。受限数据不得出现在错误体、统计、预加载 URL 或旧兼容字段中。

缓存预热后收紧分类，模拟失效通知失败，仍应拒绝；登录、退出、账号切换及旧 Promise 晚到不得回填越权内容。

### 8.2 P1.5 功能和并发验收

只有 public + 分类允许 + 当前版本获批的商品可向游客展示。members_only 不需要批准即可按原规则向登录用户销售。

每个展示写入口都撤销旧批准；价格、库存变更不触发误失效。批准 v1 时商品更新 v2，批准返回 409；同版本两个管理员操作也不能丢失撤销。

展示修改和资格失效同事务，失败全部回滚。重复保存只保留一条当前待审核记录。商家不能伪造或直接写入批准字段。

### 8.3 机器人与媒体边界验收

未绑定查询无受限商品；有效绑定保持 member 覆盖；解绑、账号失效、身份查询故障都不保留旧 member 能力。跨 audience 游标失效。

客户端文案能引导绑定，不伪称平台没有商品；群聊不会向无权群成员发送 member 商品详情。

受限商品 DTO 和分享预览不返回图片 URL；公开图片仍使用原有缓存和懒加载。已知原图片直链可能可达，这是本期明确保留的边界，不以错误测试断言其被保护。

### 8.4 验证层次

后端单元/集成覆盖统一门禁、审批 CAS、写入失效、身份解析和缓存故障。前端测试覆盖表单、状态切换和在途请求；核心 E2E 验证分类收紧、直访登录提示、审批公开及内容修改撤回。

本期不跑真实供应商，不建立模型质量 CI，也不为文档改动声称业务测试已通过。

### 9.2 P1.5 切换

### 9.4 回滚

保留增量字段和记录，优先回退 UI 或暂停新的公开申请，保留后端门禁。不要回退到完全不识别分类/审批规则的旧二进制，否则会重新暴露商品。

若确需旧版本紧急恢复，应先临时限制游客商品访问，或将相关商品受控设为 members_only 并留存可恢复记录。不能把恢复游客曝光量作为安全回滚的默认目标。

BOT-1 的实际实现（已上线）：`chatbot/audience.ts` 是新文件，作为唯一的视角来源——仅"conversationType === 'private' + platformId 有绑定 + 关联 User.status === '正常'"为 member，缺字段、未知会话类型、group、未绑定、账号非正常一律 guest，未知会话类型不默认 private。platformId 与会话类型来自客户端真实消息事件（`event.get_sender_id()` / `event.is_private_chat()`），二者参与既有 HMAC 签名，篡改即 401；客户端不让命令参数覆盖这两项，会话类型判定失败时按 group 处理（取权限更小的一侧）。绑定或用户查询抛错按原错误流程上抛，不降级为 member，也不吞成"未找到"。

详情的错误契约（已上线）：仅 403 PRODUCT_LOGIN_REQUIRED 收敛为 HTTP 200 的 `{ found: false, loginRequired: true }`，该结果不含 product、商品 ID、名称、分类、图片、价格或其他商品信息；404 保持 `{ found: false }`；其他 403、鉴权错误或服务故障继续走原错误流程。客户端据此提示"该商品需登录查看，请绑定账号后私聊机器人查询"，不再把登录限制显示成服务异常。

BOT-1 落地时同时修订了过时注释：chatbot/routes.ts 中"商品本身对访客可见"和详情"guest 视角"的说明，以及 catalog.ts 中"必须使用 member"、HMAC 等同于已绑定用户的论述。BOT-1 的定向验收已覆盖：旧请求体（无任何身份字段）→ guest、group + 已绑定 → guest、private + 未绑定 → guest、未知会话类型 → guest、private + 绑定 + 正常 → member 可见 members_only 商品、private + 绑定 + 封禁 → guest、篡改 conversationType 后签名失败、详情 403 → loginRequired 且无任何商品字段、404 保持兼容、绑定与用户查询异常不降级。

## 11. AI 重新评估的触发线

“人工无需逐件审核普通商品”改为有条件的后续目标。当前人工审核 public 申请是明确选择。

建议从以下任一情况持续 4 周时启动 AI 可行性评估：

1. 每周需要人工处理的公开申请（新增商品及公开内容实质修改）达到 30 件；
2. 实际公开审核耗时达到每周 2 小时。

这两个数是可调整的运营起点，不是行业标准，也不是自动启用开关。总商品数、库存变动或价格编辑次数不计入触发量；同一版本重复提交不重复计数。

先用当前资格记录和 AdminLog 做简单周度统计，人工记录处理工时；不为当前小规模公开申请新建监控平台。

达到触发线只启动评估，不直接放开 AI。还需要明确敏感业务政策、足够覆盖真实边界的样本、供应商条件和质量验收。若样本或质量不足，继续人工，当前功能不会被阻塞。

## 12. 暂缓 AI 的保留成果

### 12.1 只保留规范修订草案

未来若 AI 自动决定游客资格，必须显式修订 SPEC-AI-001 中“AI 仅提供人工确认建议”“不可决定 visibility”“无自动重试/路由”等冲突约定，新增仅作用于游客展示资格的有限例外。

不借“由代码最终写库”掩盖自主决策；不扩展到 RBAC、分类归属、发布、价格、库存和资金。当前 P1/P1.5 不需要此例外，不修改原规范的生效内容。

### 12.2 离线评测脚手架设计

未来脚手架只需要：人工脱敏输入、人工标签、固定版本问题、供应商单次调用适配、结果验证和本地报告。与线上数据库、发布接口和批准记录隔离。

报告比较真实业务的敏感漏放、普通误限制、人工分流比例、延迟和费用。Jev 作为文本候选，与适合中文内容的候选对照；图片能力单独评估，不把文本通过当图片通过。

本轮交付的是接口和评测范围设计，不新增或运行脚本。准备脚手架时先用人工编写的合成数据或已获准使用的脱敏数据，不擅自导出商家内容。

### 12.3 不再设置不可达到的固定样本数

撤销 600 + 1000 的通用硬门槛。样本规模由风险容忍度、类别覆盖及统计不确定性决定，合成样本用于对抗测试，不能替代真实分布。

样本小只能说明测试结果，不能据“零漏放”宣称真实漏放为零。若允许自动公开，需报告样本数、敏感分类型结果和不确定性；证据不足时 AI 仅供管理员参考，不替代人工批准。

### 12.4 删除首版预建能力

不预建任务租约、共享熔断、配置 epoch、三模式切换、模型路由和自动补检。未来实际需要后台吞吐和容灾时，再基于当时规模做最小设计。

不定期重复评估未变化内容。只有内容、业务政策，或经过验收后主动迁移模型/判断规则时考虑针对性重扫；固定模型版本不等于输出必然逐次相同，也不是安排定期付费重跑的理由。

超长、缺字段、服务失败或无法确定的内容直接保留人工，不做首版分段聚合。模型不可用时不能撤销已有有效人工批准，也不能自动批准待审商品。

## 13. 境外 AI 生产启用的硬前置

以下是本项目拟采用的上线控制，不以“商品已经公开”或“不用于训练”代替数据处理评估。

1. 明确真实外发字段、样本来源、处理目的、数据主体及供应商/子处理商/存储地域，完成书面出境与数据处理评估，并由指定负责人签署结论；适用要求交由负责该事项的专业人员确认。
2. 签订企业服务合同及数据处理协议，明确处理地域、保留/删除期限、是否训练、子处理商、事故通知、访问控制和终止删除。不能以营销文案或普通 API 账号开通代替合同。
3. 若采用 Jev，按企业协议核实并书面开通所需零数据保留能力；在普通账号上不得假定已有 ZDR。作为本项目的保守启用条件，真实商家内容进入 Jev 生产链路前需完成企业合同及 ZDR 确认。
4. 完成数据白名单和泄露测试：不外发卡密、交付内容、库存条目、购买表单答案、邮箱、凭据或内部备注。图片/OCR 服务也单独评估，不沿用文本服务的结论。
5. 从生产网络验证服务可用性、额度、费用和访问限制；固定模型版本、实测中文商品能力，完成质量验收与明确的人工降级路径。

任一前置不满足，生产不外发、不自动放行；P1/P1.5 照常运行。若企业合同、地域或预算不合适，改评估符合要求的国内服务或继续人工，不围绕 Jev 预先锁定系统。

TypeSafe 官方模型文档列出企业客户 ZDR 能力，且说明英语为主要训练语言；这不等于普通账户已零保留，也不证明中文商品检测质量。[官方模型及数据处理说明](https://docs.typesafe.ai/models)

## 14. 本期风险与剩余决策

当前产品方向已明确：BOT-1 已交付上线，P1 与 P1.5 同批上线，群内商品查询自动转私聊留给 BOT-2 联调后交付，AI 暂缓。

**已修复**：此前识别出的最大匿名访问缺口——QQ 商品接口固定使用 member 视角、未绑定用户也可能读取原本仅登录可见的商品——已由 BOT-1 关闭（master 96d345a）。当前服务端对未绑定、群聊、缺字段、未知会话类型、账号非正常一律按 guest 处理，仅"私聊 + 已绑定 + 账号状态正常"恢复 member；绑定的判定不信任请求体自报，platformId 与会话类型来自客户端真实消息事件并参与 HMAC。全库 15 件是总量，不能将总量表述为已验证可泄露的件数；BOT-1 关闭的是"member 视角被无条件使用"这条路径。

BOT-1 未实现群内商品查询自动转私聊：群内仍只返回固定引导，转私聊留给 BOT-2 验证接收者绑定、私聊交付和失败不回退后再交付。

实施前仍需核实最新远程基线、生产分类设置；机器人侧的发送者身份与会话类型可信性已随 BOT-1 落地（取自真实消息事件并纳入签名），但"已具备私聊能力"不等于"群内商品命令已安全转私聊"，BOT-2 未完成前保持固定引导，私聊发送失败不得回退群内展示 member 内容。
