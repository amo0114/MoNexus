# 运行时配置第二阶段

状态：2A/2B/2C 已实现并完成本地回归验证（2026-11-13）；尚未部署，真实渠道待受控验收。

实施与恢复说明：`../operations/runtime-settings.md`。支付当前限制为每个物理账号最多保留 8 个凭据版本，达到上限后拒绝新增；尚未提供版本退休流程。

基线：`origin/develop` + PR #353 + 第一阶段运行时配置改动。
第一阶段实现与部署边界见 `../operations/runtime-settings.md`。

## 目标与交付顺序

把短链、外部履约和支付渠道的业务参数迁入管理员后台，使新请求使用已激活配置，
并保留历史链接、履约任务和支付订单所依赖的配置。按下面三个独立交付实施：

| 交付 | 配置内容 | 生效边界 |
| --- | --- | --- |
| 2A：短链 | API origin、公开 origin、分组、加密登录凭据 | 后续创建请求；已生成链接保留 |
| 2B：FakaBridge / Xboard | 开通、状态、撤销 URL，密钥、超时、重试上限、面板地址 | 新任务绑定新版本；旧任务使用原版本 |
| 2C：支付 | Stripe、PayPal、微信支付、支付宝、VMQFox 的账号与凭据，以及新收款启停 | 新报价与订单使用已启用账号；历史交易继续使用原账号配置 |

数据库、Redis、监听器、域名/反代拓扑、加密根密钥、生产与沙箱隔离、监控和备份
继续属于部署环境。保留环境引导兼容；数据库中存在权威配置后，失败不得静默回退。

## 共同配置生命周期

管理员 MFA 和对应设置权限保护所有配置入口，查询不返回明文凭据或密文。
表单使用业务字段，不要求管理员输入环境变量名称或 JSON。

保存草稿、校验/探测、激活、停止新请求、回滚均记录版本和审计。
每次提交携带 `expectedVersion`，草稿变更使先前探测结果失效。
先记录探测意图，再请求外部服务；原始响应、完整目标 URL 和凭据不进入审计。
历史版本不可被编辑或删除，仍被业务记录引用时必须保留。

凭据使用独立的部署根密钥加密，AAD 绑定配置身份、版本与规范化目标参数。
保存时不得把旧凭据自动带到新目标。业务密文、数据库备份和根密钥分开保管。
历史版本的解密和密钥轮换也必须覆盖回滚版本，不能只重加密当前活动配置。

区分三个状态：本地参数校验通过、认证/只读探测通过、完整业务流程已验收。
不以第一种代替后两种；真实凭据缺失时使用 fixture 测试，不声明线上服务可用。

## 2A：短链

现状：`server/src/lib/shortlinkClient.ts` 的默认客户端和 token 固定在进程内。
`server/src/modules/products/shareLinks.ts` 已有创建租约、attempt token 和最终 CAS。

实施：

1. 新增草稿、活动指针和不可变配置版本，用户名/密码整体加密。
2. 每次创建操作解析一次活动版本，客户端与 token 按版本隔离；保留总 deadline。
3. 创建租约记录配置版本；完成 CAS 同时匹配 attempt token 和版本。
   已开始的请求允许使用其已绑定版本完成，激活不取消该请求。
4. 已 ready 的链接继续复用，不批量重建、改写或删除历史链接。
5. 禁用只阻止新建；已经存在且通过当前商品访问检查的链接仍可返回。
6. 登录探测只调用现有登录接口，不创建远端短链。页面明确说明登录探测不能证明
   创建接口和分组权限可用；创建能力由独立 fixture/受控验收验证。
7. 保持 HTTPS origin、禁止 userinfo/路径/query/fragment、禁止重定向等现有约束。

验收：激活后另一实例下一次创建读取新版本；旧 token 不复用；并发切换不污染新版本；
凭据不回传；旧 ready 链接保留；保存冲突、探测失败、回滚与权限测试通过。

## 2B：FakaBridge / Xboard

现状：v1 `FakaBridgeTask` 没有端点或配置版本快照，开通、查询、重试和撤销使用
当前环境配置。v2 付费重置和流量重置已有 instance/origin/client 快照，目标变化时
会拒绝执行，但没有冻结凭据版本。已成功任务仍可能在退款时进入撤销流程。

实施：

1. 新增不可变履约配置版本，任务创建事务冻结版本 ID，网络调用显式接收该快照。
   `FakaBridgeTask` 与流量重置操作均需要覆盖，不能只改首个开通请求。
2. 升级时将现有环境配置登记为历史引导版本。旧 v1 任务的归属只能绑定升级时
   可信的原目标；不能在每次激活时把所有旧任务改绑到当前目标。
   如果无法证明引导目标与历史任务一致，则保持原路径并提示处理，不猜测迁移。
3. instance ID 与 origin 是稳定身份。更换 Xboard 实例需要新身份；不得把已有
   instance ID 重新指向另一站点。保留 v2 目标、所有权和执行证据校验。
4. 开通、状态、对账、撤销、强制撤销和退款后的撤销都根据任务版本调用。
   禁用新履约不停止这些历史操作。
5. 容量、plan-catalog、账号 capability 等缓存和 in-flight 去重加入配置身份/版本。
   激活后旧探测结果不能写进新版本缓存。
6. 只读探测使用现有签名 plan-catalog/capability 路径；不得创建订阅、重置流量
   或修改远端容量。继续保留 HTTPS、固定路径和目标身份约束。
7. 面板地址用于新交付展示；不回写历史交付内容。

验收：A 版本任务在 B 激活后仍对 A 开通/查询/撤销；成功很久后退款也不改投 B；
v2 身份不匹配仍拒绝；容量并发探测隔离；跨实例生效；迁移不改订单、积分或远端状态。

## 2C：支付账号与配置版本

现状：报价、订单、attempt、event 已有 `providerAccountKey`，但没有凭据版本。
Stripe、Alipay、VMQFox 会固定客户端/配置；PayPal 的缓存 key 不包含轮换后的 secret。
回调按 provider 单一路径验签，历史查询、关单、退款与对账按账号标识工作。

设计约束：

1. 分离稳定支付账号和不可变凭据版本。账号身份与生产/沙箱环境不可变；
   新配置版本不得重新解释已有账号。Stripe 当前按 mode 使用的 `default` key
   不能自动代表任意新商户账号。
2. 报价、订单和 attempt 显式保存配置版本 ID；已存在记录允许为空并沿用原
   环境兼容路径。新报价在下单时重新验证活动版本，版本变化要求重新报价。
3. 不把凭据版本编码成新的物理账号 key：同一支付事实的事件去重仍使用稳定账号，
   防止密钥轮换让重复 webhook 被当成另一个账号的收款。
4. 历史 create recovery、complete/capture、query、close、refund 和 reconciliation
   按订单/attempt 绑定的版本构造 adapter；SDK/token 缓存按版本隔离。
5. 回调可增加稳定账号路径。路径参数只是选择候选配置，必须验签和核对渠道身份；
   轮换时保留有界的验签版本集合。验签后按渠道支付 ID 找到 attempt，并使用其
   稳定账号/版本校验，不根据未经验证的 body 选择目标或入账。
   旧 provider 路径继续服务原环境账号，不能激活后直接指向新商户。
6. 后台分别提供“接受新订单”和“保留历史处理”状态。停止新收款不能卸载历史
   webhook、查询、退款、争议或对账；回滚也不改写已有订单的配置绑定。
7. 生产/沙箱、支付事件加密、回调公开 origin 和金额 hard cap 保留部署安全边界。
   后台配置必须复用渠道现有隔离校验，不能绕过它们。
8. 没有通用 provider probe。先实现逐渠道的本地完整性校验和明确可用的只读诊断；
   不通过创建真实订单、扣款或退款来自动“测试连接”。
9. 当前支付规格 §12 的“凭据不入库”在本交付范围内需要明确修订为“只保存独立
   根密钥加密的凭据版本”；根密钥仍不入库。实施时更新该约束与恢复 runbook。

验收必须覆盖：同商户换密钥、新商户切换、迟到回调、重复事件、旧订单退款、
unknown 创建恢复、停收款后继续入账、跨实例版本切换，以及 quote/activate 并发。
复用既有 Observation → applyConfirmedPayment → Credit 入口，不修改钱包记账路径。

## 实施与验证边界

每个交付分别完成迁移、后端、管理员表单、OpenAPI、部署说明和恢复说明。
涉及外部任务或支付版本绑定的测试使用真实 PostgreSQL 与受控 HTTP/SDK fixture。
浏览器验证保存、错误反馈、探测、激活、禁用和回滚；验证凭据提交后清空与移动端布局。
任何真实部署、真实扣款和第三方系统配置变更不属于本方案的自动执行动作。
