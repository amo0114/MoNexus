## 审查域一：身份与权限

状态：已完成第一轮。已完成代码路径、路由中间件顺序和关键负路径测试；下列并发问题为实际复现的确认发现。

### 已验证

| 事项 | 结论与证据 |
| --- | --- |
| 密码与会话存储 | 密码以 bcrypt 存储；refresh token 为 40-byte 随机值，数据库只存 SHA-256 hash（`server/src/modules/auth/service.ts`）。 |
| Refresh 基本轮换 | 正常刷新会撤销旧 token 后签发新 token；已撤销 token 的顺序重放会撤销该用户其余 refresh token。 |
| 密码变更 / 重置 | 两条路径均在事务中更新密码并撤销全部 refresh token（`service.ts:287-293`、`305-311`）。 |
| 封禁即时限制 | `requireActiveUser` 位于普通业务、商家和管理员路由的角色检查之前；封禁同时撤销 refresh token 并清除本进程用户状态缓存（`admin/service.ts:156-180`）。旧 access token 访问 `/me`、积分、订单、上传和商家入口均有回归测试。 |
| 商家生命周期 | 审核通过会更新角色并撤销旧 refresh token；停用会把角色改回 user、撤销 refresh token；即使旧 access token 的 claim 仍为 merchant，`requireMerchant` 还会读 Merchant.status，因此会拒绝停用商家（`auth.ts:100-120`）。 |
| 管理员入口 | `/api/admin` 在路由组入口统一使用 `authenticate → requireActiveUser → requireAdmin`；管理员状态每次从数据库读取，不走状态缓存。 |
| CORS / Cookie | refresh cookie 是 `HttpOnly`、`SameSite=Lax` 且生产强制 `Secure`；修改业务数据的 API 使用 Bearer access token，而不是 cookie。 |
| 已执行测试 | 以 `NODE_ENV=test`、`TEST_DATABASE_URL=.../monexus_test` 运行：auth / token / active-user / refresh wiring / status-cache 共 **37** 项通过；admin / merchant 共 **38** 项通过。 |

说明：access JWT 的角色 claim 固定 15 分钟有效（`server/src/config/index.ts:171`）。商家停用有数据库状态二次校验；管理员没有产品内的“降权”接口，因此未发现可通过现有 API 造成管理员旧 token 持续越权的路径。若未来增加管理员降权或多实例部署，应将角色版本 / 会话版本纳入服务端校验。

### 确认发现

| ID | 级别 | 影响 | 证据 | 修复建议 | 回归测试 |
| --- | --- | --- | --- | --- | --- |
| AUTH-01 | P1 | 同一 refresh token 的并发请求可以同时通过轮换，生成两个仍有效的新 refresh token。攻击者一旦拿到某次 refresh token，可与用户同时刷新并在未触发“重放检测”的情况下建立自己的 7 天会话。另一种竞争顺序会撤销刚签发的 token，导致合法用户被强制登出。 | `refreshAccessToken` 先读 `revoked=false`，随后在非事务、非条件更新中执行 `update({ id })`（`auth/service.ts:152-182`）。在隔离库连续复现 20 次：19 次两请求均 fulfilled，且 `activeTokenCount=2`；1 次一成功一失败，且新 token 被全体撤销。 | 把“消费旧 token + 创建新 token”改为单个事务内的原子 compare-and-set：按 `id + revoked=false + 未过期` 条件更新，必须检查受影响行为 1；失败则按明确的重放策略撤销会话族并返回 401。为 tokenHash 建唯一约束 / 索引，并避免 `findFirst` 的歧义。 | 同一 cookie 并发发起两次 `/api/auth/refresh`：最多一个 200；其余响应符合 fail-closed 策略；最终活跃 refresh token 数不超过 1。 |

### 未确认风险与待验证项

- **AUTH-R1 / P3（扩容前处理）**：普通用户和商家的封禁状态使用进程内 60 秒 LRU 缓存。当前单实例 Compose 部署中，后台封禁会主动失效本实例缓存；若扩为多个 server 副本，其他副本最多 60 秒仍可接受旧 token，除非接入共享失效机制或将该 TTL 设为 0。此项将在部署域一并确认目标拓扑。
- **AUTH-R2 / P3（策略决策）**：注册、重置和改密密码仅要求最少 6 位（`auth/schema.ts:3-25`）。这不是逻辑绕过，但对互联网生产站点偏弱；建议确定最小长度（建议 10–12）及是否启用常见/泄露密码拦截，避免在未确认兼容策略前直接修改。
- 邮箱验证 token 的并发消费只会把同一用户的 `emailVerified` 写为时间，不构成越权；但若需要严格的一次性审计，可复用 AUTH-02 的条件消费模式。

### 结论

- 身份、封禁、商家状态和基础越权防护整体覆盖较好，现有 75 项相关测试均通过。
- AUTH-01 是本轮应优先修复的会话安全问题；AUTH-02 应紧随其后处理。两项修复都不需要迁移生产业务数据，但 AUTH-01 的 tokenHash 唯一索引若上线需先执行重复 hash 检查（正常情况下随机值不应重复）。
- 在修复前，不建议将 refresh-token 重放保护作为账户被盗后的可靠会话收敛机制。完成修复和回归后进入积分与订单账务审查。

## 审查域二：积分与订单账务

| 已执行测试 | `orders`、`instant-fixed`、会员等级和系统配置共 **41** 项通过；人工履约状态机与自动关闭 cron 共 **13** 项通过。它们覆盖了正常/顺序路径和多种负路径，但均未覆盖本节的同用户并发下单、同订单重复终结和余额-流水对账。 |

### 未确认风险与待验证项

- PointAccount 目前没有数据库 `CHECK (balance >= 0)`；这不是 ACCT-01～03 的根因，但没有最后一道数据完整性防线。需要在采用冻结模型时一并设计（若余额允许临时负数则必须有明确账务定义）。
- 即时库存抢购不会将同一库存项重复售出，但并发请求可能同时挑到第一条库存、其中一笔因条件更新失败而回滚，即使后面仍有库存。这是可用性/重试体验问题，待商家库存域评估是否改为数据库行锁/跳过锁定行。

### 结论

- ACCT-01、ACCT-02、ACCT-03 直接破坏余额、订单和结算的不变量，应作为 P0 阻断项处理。它们共享两个根因：积分账户没有原子可用余额操作，订单状态机没有原子比较并交换。
- 建议不要分别打补丁；先确定“可用余额 + 冻结余额 + 流水类型”的单一账务模型，再把所有订单、退款、管理员调整、签到和邀请入口迁移到统一账户服务。这样才能避免修复一个出口而在 cron 或仲裁中留下同类问题。

## 审查域三：人工服务履约、争议与仲裁

状态：已完成第一轮。权限归属和正常状态流转基本正确，但终态结算没有按履约模式完整收口；本域还继承 ACCT-03 的状态 CAS 缺失。

### 已验证

| 事项 | 结论与证据 |
| --- | --- |

## 汇总与修复建议

### 阻断上线 / 交易扩大的 P0

1. **ACCT-01**：并发即时下单少扣积分；
2. **ACCT-02**：人工单冻结不占用余额，允许负余额；
3. **ACCT-03 / FUL-03**：状态机不是原子 CAS，可重复终态和扣款；
4. **FUL-01**：即时订单管理员退款不返还积分；
5. **INV-01**：并发库存导入可复制发货秘密。

### 推荐实施次序
