# MoNexus 全功能链路 Review 手册

- 建立日期：2026-07-23
- 审查类型：代码、接口契约、状态一致性、权限边界、部署运行面
- 审查范围：当前 master 已合并的功能；生产运行环境不写入真实业务数据
- 审查原则：先收集证据，再给结论；发现不等于漏洞，复现成功后才标记为确认问题

## 1. 目标与交付

本 review 的目标不是重新实现功能，而是回答以下问题：

1. 每条用户可见链路是否可端到端走通；
2. 权限、积分、库存、订单状态和结算是否保持正确的不变量；
3. 错误、并发、重试、过期 token、重复请求和跨角色访问时是否安全；
4. 前端显示与后端接口契约是否一致；
5. 生产部署是否能发现、限制、恢复和追溯故障。

每个审查域将输出：

| 输出 | 内容 |
| --- | --- |
| 链路图 | 参与者、状态、写入对象和外部依赖 |
| 覆盖证据 | 现有单元、接口、E2E、运行手册和实际代码位置 |
| 发现 | 证据、影响范围、复现前提、严重程度与修复建议 |
| 未确认风险 | 需补测试、需 staging 或需业务决策才能结论的项目 |
| 回归项 | 修复后必须新增或更新的测试 |

## 2. 风险分级与证据规范

| 级别 | 判定标准 | 处理期望 |
| --- | --- | --- |
| P0 / Critical | 未授权管理权限、可直接造成余额/库存损失、敏感数据大规模泄露、生产不可恢复中断 | 立即限制入口并优先修复 |
| P1 / High | 可跨用户或跨商家操作资源、订单/结算明显错误、可稳定绕过关键业务限制 | 当前迭代修复并补回归测试 |
| P2 / Medium | 错误状态、边界条件、可恢复一致性问题、明显错误体验 | 排入近期修复 |
| P3 / Low | 文案、非关键可观测性、维护性或优化项 | 记录并按容量处理 |

确认发现必须至少包含：

- 精确的代码或接口位置；
- 攻击者/操作者身份与前置条件；
- 实际影响而非推测性描述；
- 最小复现路径，或对应测试用例；
- 不破坏现有数据的修复与回归建议。

审查过程不得：

- 输出、提交或请求生产密码、令牌、私钥、用户隐私；
- 在生产库执行 seed、重置、批量修改或破坏性并发测试；
- 将前端路由守卫当作后端鉴权证据；
- 把未复现的问题表述为已确认漏洞。

## 3. 全局不变量

以下规则跨越多个模块，逐项 review 时必须反复验证：

1. 角色、封禁状态和商家审批状态必须由服务端强制执行；
2. 用户只能读取或操作自身的订单、积分、资料和私有发货内容；
3. 商家只能操作自己的商品、库存、订单和结算记录；
4. 管理操作必须有管理员鉴权，必要时具备审计记录；
5. 积分余额不得因重试、并发、拒单、争议或自动关闭出现重复扣减/重复返还；
6. 一个库存项只能被一个订单消费，任何交付内容不得越权泄露；
7. 订单状态转移必须合法、可追溯，状态与 Settlement、Delivery、PointLog 一致；
8. 公告、上传和公开接口只能暴露明确允许的字段与对象；
9. 生产反代、cookie、CORS、对象存储和监控端点不应扩大公开攻击面；
10. 每项关键修复都应有自动化回归测试。

## 4. 审查域一：身份与权限

### 资产与入口

- 注册、登录、登出、Refresh Token、个人资料、改密；
- 忘记密码、重置密码、邮箱验证；
- 普通用户申请商家、管理员审核商家、管理员角色；
- 前端用户态、JWT role claim、Cookie 与服务端用户状态。

主要实现位于 server/src/modules/auth、server/src/middlewares/auth.ts、前端登录页、
用户状态 store 与 RoleGuard。

### 必查场景

| 场景 | 预期 |
| --- | --- |
| 注册、重复注册、邀请码注册 | 用户唯一、奖励和邀请关系只按规则写入 |
| 错密码、过期 token、伪造 token | 一律拒绝，不泄露账号存在性或内部细节 |
| Refresh Token 轮换与重放 | 旧 token 重用会收敛到对应会话族失效 |
| 改密、重置密码、封禁 | 旧会话不能继续获得受保护资源 |
| 普通用户访问 admin/merchant API | 服务端返回 401/403，不能靠前端拦截代替 |
| 商家审批或管理员提升后的旧 JWT | UI 与 API 均能安全更新角色，旧 token 不可越权 |
| 跨用户访问 me、订单、上传、密码重置 token | 不能读取或修改他人资源 |
| CORS 与 cookie | 仅允许生产前端源，Secure/HttpOnly/SameSite 配置符合 HTTPS 部署 |

### 审查方法与证据

1. 阅读认证控制器、服务、JWT 生成与 refresh token 存储逻辑；
2. 对照中间件顺序与所有高权限路由；
3. 阅读 auth、refresh、active-user、admin、merchant 相关测试；
4. 使用隔离测试库模拟角色变化、封禁、旧 token 与跨用户请求；
5. 核对前端角色刷新仅用于体验，不构成安全边界。

### 完成标准

- 登录、刷新、退出、改密、封禁和角色切换的 session 失效语义明确；
- 所有管理员/商家路由均有服务端身份与角色校验；
- 高权限身份变化具有至少一条接口级回归测试；
- 发现按 P0-P3 分类并给出修复顺序。

## 5. 审查域二：积分与订单账务

### 资产与入口

- PointAccount、PointLog、签到、注册/邀请奖励、会员加成；
- 创建订单、冻结积分、即时扣减、关闭、退款、仲裁、结算；
- 库存扣减与失败回滚。

### 核心不变量

~~~text
余额变化 = 所有已生效积分流水的代数结果
同一业务动作只产生一次账务效果
即时发货：扣减积分后才交付
人工服务：创建时冻结，完成/关闭时才正式扣减
退款：不能让同一笔金额重复返还
~~~
### 必查场景

| 场景 | 预期 |
| --- | --- |
| 同一用户快速重复下单 | 不能超扣、不能获得两份同一库存 |
| 两个用户抢最后一份库存 | 最多一单成功，失败方余额与库存保持一致 |
| 即时库存、固定内容、人工服务 | 三种模式的扣分、Delivery、Settlement 状态分别正确 |
| 余额不足、产品下架、库存为空 | 原子失败，不写残留订单或流水 |
| 用户关闭、商家拒单、管理员退款 | 余额、冻结、Settlement、状态事件彼此一致 |
| 自动关闭重试/重复执行 | 幂等，不重复扣分或创建结算 |
| 签到与等级加成 | 响应字段、余额、流水、当天唯一记录一致 |
| 管理员调整积分 | 原因、操作者、金额和余额结果可审计 |

### 审查方法与证据

1. 阅读 orders、points、fulfillment、memberTier、systemConfig 服务；
2. 列出事务边界、唯一约束、乐观/悲观并发控制和错误回滚点；
3. 对照订单、库存、积分、会员等级与系统配置测试；
4. 在可丢弃数据库做并发 API 测试；
5. 对同一订单重复调用关闭、拒单、仲裁等接口。

### 完成标准

- 三种履约模式的账务矩阵完整；
- 关键状态改变存在幂等或重复请求保护；
- 并发库存测试覆盖最后一个库存项；
- 所有确认不一致均附账务修复策略与数据修复影响评估。

## 6. 审查域三：人工服务履约、争议与仲裁

### 状态模型

~~~text
pending -> processing -> delivered -> closed
pending -> refunded
delivered -> disputed -> processing / delivered / closed / refunded
~~~

即时交付模式创建后直接进入 delivered；人工服务从 pending 开始。争议恢复目标应当
依交付模式不同而不同。超过规则期限的 delivered 订单由 cron 自动关闭。

### 必查场景

- 非订单所属用户发起争议、关闭或评价；
- 商家对不属于自己的订单接单、发货、拒单、回应争议；
- 在错误状态调用履约接口，或同一接口重放；
- 争议中商家恢复履约、管理员裁决退款/关闭；
- 自动关闭与用户手动关闭同时发生；
- 状态事件、Delivery、PointLog、Settlement 和库存的最终一致性；
- 时间边界、时区、SLA 超时显示与 cron 失败可观测性。

### 完成标准

- 状态转移表与代码实际允许的转移一致；
- 每个终态的资金、交付和结算结果明确；
- cron 可安全重复执行且有失败日志/指标；
- 争议和仲裁的权限链条有接口测试。

## 7. 审查域四：商家、商品与库存

### 范围

- 商家申请、审批、拒绝、暂停、佣金；
- 商品创建、编辑、下架与多图；
- instant_inventory、instant_fixed、manual_service 三种交付模式；
- 库存导入、预览、作废、日志、低库存；
- 商家订单、统计和结算查询。

### 必查场景

| 场景 | 预期 |
| --- | --- |
| 商家 A 访问商家 B 的产品、库存、订单、结算 | 404 或 403，不泄露内容 |
| 未审批/暂停商家 | 不能创建商品、处理订单或查看商家敏感数据 |
| 切换交付模式 | 固定内容、库存模式、库存量和验证规则保持一致 |
| 导入库存含空项、重复项、超量项 | 可预览、可拒绝、可审计，不能局部写坏 |
| 即时库存发货内容 | 只向对应买家订单返回，列表接口不泄露 |
| 人工服务商品 | 不错误使用库存接口或即时发货路径 |
| 佣金与结算 | 商家可见金额与管理员结算金额一致 |

### 完成标准

- 所有资源查询按 merchantId 或 ownerId 约束；
- 库存明文不出现在商品公共接口、日志或无权订单中；
- 每种交付模式都有创建、编辑、下单和异常测试；
- 商家审批状态对 API 的实际限制已验证。

## 8. 审查域五：管理后台与治理

### 范围

- 总览指标、用户封禁/解封、积分调整；
- 商品与库存管理、商家审核、佣金与结算；
- 订单仲裁、评价删除、公告、系统配置、审计日志。

### 必查场景

- 普通用户、商家和失效管理员访问每个 admin endpoint；
- 管理员是否能封禁自身、重复审核、重复结算或仲裁非争议订单；
- 批量结算包含非 pending 记录时是否整体失败；
- 调整积分、仲裁、审核、系统配置是否留下足够审计信息；
- 审计日志是否避免泄露密码、token、库存发货内容；
- 管理仪表盘统计是否受时间边界、软状态和缓存影响。

### 完成标准

- 高权限端点有一致鉴权、输入校验、可追溯审计；
- 批处理原子性与失败语义清晰；
- 敏感管理操作都有针对负路径的测试。

## 9. 审查域六：公告、评价、上传与前端体验

### 范围

- 公告的草稿、发布、归档、时间窗、优先级和受众；
- 订单评价、商品评价公开展示、管理员删除；
- 图片上传、对象存储 URL、MinIO 反代；
- 登录、商品页、个人中心、商家和管理员前端状态与错误提示。

### 必查场景

- 访客只能读取 audience=all 且处于有效时间窗的公告；
- Token 角色改变后公告受众与前端横幅同步；
- 非订单用户不能创建/编辑评价；删除评价需要管理员；
- 上传 MIME、大小、文件扩展、对象 key、公开 URL 与访问控制；
- 前端与 API 返回字段名称、空值、加载/失败/重复点击状态；
- 移动端与桌面端主要操作是否可访问且不会暴露开发入口。

### 完成标准

- 公开接口不泄露后台字段、草稿或定向内容；
- 上传失败映射为正确 HTTP 错误，生产对象存储不意外公开写入；
- 已发现的前后端契约差异都有类型、测试或运行时保护。

## 10. 审查域七：部署、安全、备份与可观测性

### 范围

- Docker/GHCR 多架构镜像、Prisma 引擎、Compose 网络和 volumes；
- Cloudflare、1Panel OpenResty、TLS、反向代理、CORS、Cookie；
- 健康检查、日志、指标、Sentry、Redis 降级；
- 迁移、发布、回滚、Postgres 与 MinIO 备份恢复。

### 必查场景

- AMD64/ARM64 镜像 manifest、容器实际架构、Prisma engine；
- 仅反代服务公开 80/443，Web 与数据库绑定到私网/loopback；
- Full (strict) TLS、Cookie Secure、可信代理数与速率限制来源 IP；
- readiness 在数据库、配置、Redis 异常时的语义；
- 镜像 tag pin、发布前 manifest 检查、回滚后的 schema 兼容；
- 备份是否加密/异机、是否可用独立环境恢复；
- metrics 是否受 token 保护，日志是否脱敏。

### 完成标准

- 部署拓扑、端口暴露和 TLS 链路被实际命令验证；
- 关键运行失败有可定位日志与健康状态；
- 备份与恢复步骤可执行，且不会误删生产 volume；
- 运维文档与现有 Compose 实现一致。

## 11. 执行顺序与报告模板

建议按以下顺序执行，因为前项是后项的安全前提：

1. 身份与权限；
2. 积分与订单账务；
3. 人工服务履约与争议；
4. 商家商品与库存；
5. 管理后台；
6. 公告、评价、上传与前端；
7. 部署、安全、备份与可观测性。

每个审查域结束后，在本文或配套报告中使用以下模板记录：

~~~markdown
## <审查域名称>

状态：进行中 / 已完成 / 需要外部信息

### 已验证
- <链路、测试或代码证据>

### 确认发现
| ID | 级别 | 影响 | 证据 | 修复建议 | 回归测试 |
| --- | --- | --- | --- | --- | --- |

### 未确认风险与待验证项
- <为什么尚无法结论，以及需要什么证据>

### 结论
- <是否适合进入下一审查域>
~~~
