# 主工作区公共业务规则规范化

## 范围

在现有服务拆分基础上，统一公共规则和依赖方向。修改位于主工作区，保留原有
未提交功能改动。没有数据库结构迁移，也没有执行提交、发布或线上修改。

## 第一轮：业务时间与交付文件

- `lib/businessTime.ts` 增加上海自然日、自然月的真实时间戳范围。
- 管理员今日统计、商家日/月报表、每日消费验证改用上海口径；商家报表 SQL
  同时按上海日期分组。时间戳范围采用左闭右开，不能使用日历日期的 UTC 零点
  存储值代替上海零点的真实时刻。
- 签到及机器人默认日期复用已有 `businessDateString`。
- 文件绑定与交付附件统一调用 `catalog/deliveryFileOwnership.ts`。商家层保留
  小型兼容包装。调用方继续传入原有事务；不存在或归属不符返回 404，已撤销或
  删除的自有文件返回 400。

## 第二轮：消费限制、分页与状态规则

- `points/spendingPolicy.ts` 统一预览和事务扣款的消费限制判定；订单、结算预览、
  推广积分扣款直接依赖此模块。充值开关、渠道与充值限制仍归充值模块。
- `lib/paginationPolicy.ts` 处理纯分页规范化，`lib/pagination.ts` 负责读取动态配置。
  配置写入与管理员用户/订单查询共享 500 的绝对上限。
- 管理员用户和订单列表：省略大小时使用动态默认值；有效输入按动态上限截断；
  大于 500 的输入返回 400。原来请求 101 即被 schema 拒绝，现在可进入配置策略，
  默认配置下会被截为 100；配置上调后可返回更大页。OpenAPI 已同步。
- 商家商品/库存分页保留原有大输入截断契约。审计、排行榜等固定分页接口不自动
  迁入动态策略；这些是显式的接口限制。
- `orders/statusPolicy.ts` 独立保存状态、履约模式、旧状态映射及合法迁移判断。
  结算资格、DTO 和序列化依赖纯规则；数据库迁移及通知继续由 `fulfillment.ts`
  执行。旧入口保留兼容导出。

## 第三轮：共享身份、配置锁与 Faka 编排

- `orders/provisioningConfig.ts` 保存自动开通配置的共享读锁及并发测试注入点。
  下单和规格开关校验使用同一入口；配置轮换/撤销的写锁仍由商家配置用例持有。
- `merchant/identity.ts` 提供跨模块的最小商家身份查询，分类申请和保障路由不再
  调用商家资料管理服务。原有 404 语义和路由权限校验保留。
- 以下文件从 `lib/fakaBridge` 迁至 `modules/fakaBridge`，业务实现逐一核对未变，
  仅调整导入位置：`worker.ts`、`lifecycle.ts`、`outbox.ts`、`paymentBackfill.ts`、
  `provisionEmailProof.ts`。外部用例通过业务入口调用，协议工具继续走基础设施入口。
- 开放 Faka 任务计数归入 `fakaBridge/taskQueries.ts`，商品价格策略保留为纯规则。
- 架构检查发现原有 `ai/generation.ts` 与 `ai/task.ts` 的静态循环；提取
  `ai/featurePolicy.ts` 保存功能、角色和配额规则，原入口保留兼容导出。

## 自动约束

`npm run check:architecture` 使用 TypeScript 语法树扫描后端生产源码，检查：

- 基础设施禁止反向导入业务模块。
- 跨模块禁止导入 admin 内部实现；商家身份仅通过明确的身份入口开放。
- 拆分后的实现禁止反向导入本模块服务聚合入口；HTTP controller 可调用公开入口。
- 指定纯规则禁止依赖数据库、流程模块或外部运行时包。
- 静态运行时依赖不得形成环；类型依赖不计入运行时环。字面量动态导入接受边界检查，
  不作为静态初始化依赖；计算生成的动态路径不在静态检查范围内。
- OpenAPI 内部引用可解析，且保留商品模板接口契约。

`npm run test:architecture` 验证扫描与约束本身。CI 架构任务安装根目录依赖后执行
规则测试和实际扫描；Node.js 版本使用项目声明的 22。

webhook 配置生命周期竞争，以及商品和保障的相关回归。
