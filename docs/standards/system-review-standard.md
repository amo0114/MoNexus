# 系统评审标准（System Review Standard）

> 版本 v1.0 · 生效 2026-11-08
> 适用：MoNexus 及同构项目（电商 / 资金 / 多租户 / AI 集成 / 前端体验型）
> 定位：本文件定义**什么算审查过、什么算证明过、什么条件才允许发布**。
> 它约束的是评审本身，不是某一个项目。项目特有的内容放在 `docs/reviews/<基线>/02-invariants.md`。

---

## 0. 这份标准要解决的问题

AI 时代的代码评审有三个系统性失效，本标准的每一条设计都针对其中之一：

| 失效 | 表现 | 本标准的对策 |
| --- | --- | --- |
| **审错了对象** | 让 AI 检查"另一个 AI 是否按（可能错误的）需求写对了代码" | 先审**契约**（不变量），再审实现（§2、§4） |
| **把结论当证据** | "32 个场景全部通过"但没有场景定义、环境、断言范围 | 证据分级 + 禁止无证据的"通过"（§5） |
| **把复杂度当成熟** | 抽象层、设计模式、微服务拆分被当作工程质量 | 复杂度单独作为审查对象并计入门禁（§3.5） |

一句话概括本标准的立场：

> **过去的 Code Review 问「代码有什么问题」；系统评审要问「我们有哪些关于系统正确性的假设，尚未被证实」。**

---

## 1. 审查关注顺序：12 个维度

12 个维度**不平均重要**。下表是**审查顺序**，不是风险等级——具体问题的严重度按 §6 的 P0–P3 判定。

| # | 维度 | 核心问题 | 优先级 |
| --- | --- | --- | --- |
| 1 | 需求与业务语义 | 系统是否真正解决目标问题？ | P0 |
| 2 | 业务不变量与状态机 | 有没有绝对不能违反的规则？ | P0 |
| 3 | 数据模型与一致性 | 数据在并发、失败、重试后是否仍正确？ | P0 |
| 4 | 安全与信任边界 | 有没有越权、泄露或绕过路径？ | P0 |
| 5 | 架构与模块边界 | 职责、依赖和复杂度是否合理？ | P1 |
| 6 | 异常处理与可靠性 | 局部失败是否会导致系统性故障？ | P1 |
| 7 | 测试与可验证性 | 是否有足够证据证明系统正确？ | P1 |
| 8 | 性能与资源效率 | 是否存在真实瓶颈、资源泄漏？ | P1 |
| 9 | 可观测性与可运维性 | 出问题后能否发现、定位和恢复？ | P1 |
| 10 | 代码质量与可维护性 | 未来修改是否安全、可理解？ | P2 |
| 11 | 用户体验与交互一致性 | 用户能否正确、高效地完成任务？ | 按项目定 |
| 12 | 交付、部署与演进能力 | 能否安全发布、回滚和持续演进？ | P1 |

### 1.1 维度权重必须按项目类型调整

不存在通用权重。开审前必须在 `00-baseline.md` 里显式声明本项目类型与加权理由。

| 项目类型 | 必须提高权重的维度 |
| --- | --- |
| 电商 / 资金平台 | 资金与账本一致性、库存、履约、佣金、权限 |
| 安全网关 | 入口覆盖、策略正确性、绕过路径、失败策略、审计证据 |
| 智能售后 / Agent | 状态持久化、重复执行、interrupt/resume、人工接管、工具权限 |
| 个人数字主场 | 私有与公开数据隔离、SSRF、部署安全 |
| 基础设施 / 监控 | 故障隔离、凭据管理、部署回滚、备份恢复、可观测性 |
| 视觉体验型前端 | 交互、可访问性、响应式、视觉一致性、真实设备测试 |

### 1.2 AI 集成项目的强制附加项

涉及 LLM 的项目，在上述维度之外**必须**额外覆盖：

- Prompt Injection（用户输入 / 检索内容 / 工具返回 三类来源分别验证）
- 工具调用授权（模型不能凭自己决定越权）
- 模型输出校验（结构化输出的 schema 校验与降级，不能直接落库）
- 模型不确定性（超时、空响应、拒答、截断的处理）
- 上下文泄露（多租户会话隔离、历史消息不串户）
- 成本上限（单请求与单用户配额，防止无限循环烧钱）
- 模型降级（provider 不可用时的行为）

## 2. 先审契约，再审实现

### 2.1 为什么必须先定契约

先确定"系统必须永远为真的事情"，再判断代码是否满足它。否则你只是在让 AI 检查另一个 AI 是否忠实地实现了错误的需求。

### 2.2 不变量的写法

每条不变量必须可判定（能写出反例），并且必须说明**强制机制在哪一层**：

```
INV-xx  <一句话陈述，形如"X 绝不能导致 Y">
├── 业务含义：违反后用户/平台会怎样
├── 强制机制：DB 约束 / 应用层 CAS / 事务隔离 / 唯一索引 / 仅靠约定（= 没有强制）
├── 覆盖范围：哪些入口/状态转换/异常路径受保护，哪些不受
├── 状态：VERIFIED / PARTIAL / GAP / NOT_VERIFIED
└── 证据：代码位置 + 测试或运行证据
```

**"仅靠约定"必须写成 GAP。** 注释里写"调用方必须先检查 X"、README 里写"每个退款路径都调用 Y"——在没有强制机制时，这些都是 GAP，不是 PARTIAL。

### 2.3 状态机审查清单

对每个有状态字段，回答：

1. 状态全集是什么？在 DB 里有 CHECK 约束吗？
2. 允许的转移是什么？转移表是**唯一权威实现**吗？
3. 谁能写这个字段？有没有绕过转移器的写入点（`update` 里直接写 status）？
4. 转移是否用了 CAS（`where status = 旧值`）？并发两个转移会怎样？
5. 有没有**终态死路**——进入后既无法前进也无法退出？（这是最常见的真实缺陷）
6. 有没有驻留态——只能靠人工改库才能离开？
7. 状态变更是否留痕（事件表）？

审状态机时特别警惕：**"某个状态没有出口"比"某个转移没校验"严重得多**。前者是用户资金黑洞，后者通常还有一个入口能纠正。

## 3. 资金与数据一致性：三个时刻 + 五类场景

### 3.1 三个时刻

| 时刻 | 要回答的问题 |
| --- | --- |
| **执行前** | 前置条件是否有效？检查是否在锁内/事务内？TOCTOU 窗口存在吗？ |
| **执行中** | 并发会怎样？局部失败会怎样？死锁与锁顺序？ |
| **执行后** | 状态可恢复吗？崩溃后重放安全吗？有对账出口吗？ |

### 3.2 五类场景（每一项都要单独给结论）

正常执行 / 并发竞争 / 超时 / 重试 / 进程崩溃。

同一操作在这五种场景下，必须保持规定的不变量，并明确恢复语义。**只测正常执行等于什么都没验证。**

### 3.3 必须检查的具体项

- **条件更新**：读-改-写是并发缺陷的高发形态。`if stock > 0: stock -= 1` 必须变成 `UPDATE ... SET stock = stock - 1 WHERE stock > 0 RETURNING`。
- **数据库约束**：应用层校验会在并发下失效，DB 约束不会。资金表、状态列必须有 CHECK / UNIQUE / FK。
- **幂等**：重放同一请求必须不产生第二次副作用。幂等键应落在 DB 唯一约束上，不能只在内存或 Redis。
- **事务边界**：远程调用必须在事务外（否则长事务 + 长锁）。事务内必须有超时配置。
- **锁顺序**：所有路径对同一组资源必须用一致的加锁顺序，否则 ABBA 死锁。要把锁顺序写成明文规则并抽样验证。
- **整数与金额**：货币/积分用浮点即缺陷。确定舍入方向与舍入发生的时机（入账时还是展示时）。
- **对账**：系统必须能独立回答"我的记录和外部世界的记录是否一致"。没有对账能力的资金系统，等于没有可观测性。

### 3.4 Safety vs Liveness 必须分开评

- **Safety（安全性）**：不应该发生的事永远不发生。例：同一笔支付不重复入账。
- **Liveness（活性）**：应该完成的事最终有机会完成。例：已付款的订单最终进入可处理的异常状态，而不是永久卡住。

一个系统可以满足其中一个而不满足另一个。**报告里必须分别给出结论**，混在一起会掩盖"资金出不去"这类问题。

### 3.5 复杂度也要审

在同样满足要求的前提下，优先选择边界清晰、组件更少、故障模式更容易理解、维护成本更低的实现。

要判断的是：

| 检查对象 | 判断 |
| --- | --- |
| 模块边界 | 高内聚、低耦合？ |
| 依赖方向 | 循环依赖、跨层调用？ |
| 责任归属 | 关键业务规则是否只有**唯一权威实现**？ |
| 技术选型 | 真的需要消息队列/缓存/微服务？ |
| 扩展能力 | 新增功能要改多少无关模块？ |
| 复杂度成本 | 有没有同样可靠但更简单的方案？ |

**要同时防两种病**：过度设计（大量抽象、设计模式、不必要的分布式组件）与架构欠缺（无边界、重复实现、规则散落）。

一个简单的模块化单体，完全可能优于拆分不合理的微服务。**AI 生成了大量抽象不等于工程成熟。**

## 4. 安全：不能只看"有没有鉴权中间件"

### 4.1 强制覆盖项

- 身份认证与授权是否贯穿**所有**入口（包括新加的、内部的、管理端的、代理入口）
- 多租户/多用户数据是否真正隔离（不是"接口上带了 userId"）
- IDOR：直接对象引用。用**差分探测**验证——用 B 的身份请求 A 的真实 ID，与请求不存在的 ID，响应必须一致且非 2xx
- Webhook / 回调 / 文件上传是否具有**独立**验证（不能复用普通用户鉴权）
- SSRF / SQL 注入 / XSS / 密钥泄露
- 管理端、内部接口、代理入口是否可能绕过保护
- 对外部 API、Agent 工具、第三方数据源的信任边界

### 4.2 "唯一入口"陷阱

不能因为某个入口存在防护，就假定系统所有流量都经过它。

审查时必须枚举**实际执行层**：有多少条路径能到达这个敏感操作？每条的守卫是什么？守卫是加在路由上还是加在服务函数里？如果只加在路由上，那么任何新增的调用方都会绕过它。

**正确做法**：敏感操作的前置检查应尽可能下沉到不可绕过的层（服务函数内部、DB 约束），路由守卫是补充而非唯一防线。

### 4.3 信任边界的三类对象

分开评估，不能一概而论：

1. **客户端输入**：默认完全不可信。特别注意"客户端传了一个 id，服务端用它来选择执行器/策略/租户"这类设计。
2. **第三方系统**：默认不可信且不可靠。它的"不存在"不等于"没发生"，它的"成功"需要证据。
3. **内部服务/模块**：在进程内是可信代码，但一旦能通过配置或数据被指向任意实现，信任就被放大成攻击面。

## 5. 证据：这是本标准的重心

### 5.1 三类结论

任何评审结论必须落在以下三类之一：

| 类别 | 定义 | 写法要求 |
| --- | --- | --- |
| **已验证** | 有复现和运行证据支持 | 必须给出命令 + 输出 + 断言 |
| **已证实缺陷** | 存在明确反例或错误证据 | 必须给出触发条件 + 可复现的失败 |
| **尚未验证** | 缺少证据，不能推断通过 | 必须给出验证方案与阻塞条件 |

### 5.2 五级证据强度

| 级别 | 证据 | 能支撑的结论 |
| --- | --- | --- |
| E1 | 真实环境运行、并发/故障注入、可复现 | 已证实缺陷 / 已验证 |
| E2 | 真实数据库/真实依赖的集成测试 | 已证实缺陷 / 已验证（限该场景） |
| E3 | 单元测试（含 mock） | 只能支撑"该单元行为符合其自身断言" |
| E4 | 静态路径推演（代码可证明的逻辑缺陷） | 已证实缺陷（限逻辑可证部分），其余只能"尚未验证" |
| E5 | 阅读印象 / 命名推断 / 文档声明 | **不能支撑任何结论** |

**硬规则**：

1. 禁止把"没有发现问题"写成"验证通过"。没发现问题只说明你的探测没打到，不说明不存在。
2. 文档（Spec / README / 注释）声明的事实属于 E5，必须回到代码或运行证据核实。**注释写了"每个退款路径都调用 X"，这句话本身不是证据。**
3. 测试通过 ≠ 系统正确。如果测试与实现由同一个推理过程产出，它们可能一起错。测试只能证明"实现符合测试作者的理解"。
4. 每一份报告的"未覆盖范围"是必填项，且必须比"已覆盖范围"更保守。

### 5.3 独立验证原则

- **审查者与修复者必须职责隔离**。验证不能仅依赖修复者的自我报告。
- 修复后的复核者应重新构造反例，而不是复跑修复者提供的测试。
- 对于 P0 结论，至少需要一次**独立复现**（另一个人/另一条路径得到同样结果）。

## 6. 风险分级：按实际严重度，不按审查顺序

| 级别 | 判据 | 典型例子 |
| --- | --- | --- |
| **P0** | 无特殊前置条件即可造成资金损失、资产污染、越权、数据泄露；或系统进入不可恢复的错误状态 | 并发超卖；重复入账；用户已付款却永不到账且无出口；任意用户读他人订单 |
| **P1** | 特定但现实的条件必现的处置缺陷；或系统性纵深防御缺失 | 某类订单退款必然失败；管理端某操作可让状态机进入非法态 |
| **P2** | 健壮性、可观测性、运维能力缺口——不会立即造成损失，但会延长故障时间 | 无告警；无对账出口；重试无上限 |
| **P3** | 一致性、可维护性、文档分叉、技术债 | 注释与代码不符；重复实现；命名误导 |

定级时同时考虑三个因子，并在卡片里写出来：

- **影响范围**：影响多少用户/多少资金
- **可触发性**：需要什么前置条件，攻击者/普通用户能不能做到
- **可恢复性**：出问题后能否自动或人工恢复

**注意区分"真实缺陷"与"设计取舍"与"技术债"与"未验证风险"**——这四类在报告里的处置建议完全不同，混为一谈会让团队把时间花错地方。

## 7. 分阶段评审流程 G0–G5

每个阶段有明确的准入与交付标准。**没有完成 G0 就不该开始 G2。**

### G0 — 基线与范围确认

冻结：Git commit、工作区状态（含未提交改动）、依赖版本、运行环境。

交付：
- `00-baseline.md`：commit SHA、工作区偏差及其影响、依赖与运行时约束、代码/测试/约束规模、API 与入口清单、**审查盲区声明**
- 环境能力声明：能不能构建、能不能跑测试、有没有可弃数据库、能不能连生产只读

**关键要求**：环境限制必须写清楚。如果构建跑不起来，那么所有"构建产物相关"的结论一律 NOT_VERIFIED，不能因为"代码看起来对"就默认通过。

### G1 — 业务建模与关键路径识别

交付：
- `01-architecture-map.md`：业务域、模块依赖（含循环）、数据关系、状态机、副作用清单、权限矩阵
- `02-invariants.md`：核心不变量清单（§2.2 格式），明确哪些行为绝对禁止

准入：G0 完成。这一阶段**只描述事实，不做质量判断**。

### G2 — 静态审计与架构分析

从请求入口追踪到数据落库，核查模块边界、关键实现、事务与授权路径。

交付：`raw/` 下按域拆分的原始报告，每个问题定位到具体代码与触发条件。

**关键要求**：所有结论在 G2 阶段最高只能到 E4（静态可证）。任何依赖运行时的判断必须标 NOT_VERIFIED 并给出验证方案。

### G3 — 动态验证与对抗性测试

在隔离环境验证：并发、重复提交、异常恢复、越权、恶意输入、资源限制。

前置条件（缺一不可）：
- 可弃数据库或隔离环境
- 明确禁止触碰生产数据
- 每个验证项可重复执行

交付：动态证据，以及**回填 G2 阶段的 NOT_VERIFIED 项**。本阶段可以把结论升级到 E1/E2，也可以**降级或否定** G2 的判断——后者同样有价值，必须诚实记录。

### G4 — 风险分级与修复决策

按影响范围、可触发性、严重程度、修复代价排序。

交付：`03-findings.md`（去重后的发现清单）+ 修复排期建议。

**关键要求**：区分真实缺陷 / 设计取舍 / 技术债 / 未验证风险。给出"不修"的理由同样重要。

### G5 — 修复复核与交付门禁

修复后重新执行相关不变量测试、关键回归及部署检查。

交付：`04-release-verdict.md`——明确的发布结论（§8）。

**关键要求**：复核者 ≠ 修复者。复核要重新构造反例，不是复跑修复者的测试。

## 8. 发布结论：只有四种

不许用分数代替结论。"代码质量 85 分"会掩盖上线阻断项。

| 结论 | 条件 |
| --- | --- |
| **允许发布** | 无 P0；P1 已知且有明确缓解；所有关键不变量状态为 VERIFIED |
| **有条件发布** | 无 P0；P1 存在但影响面被功能开关/灰度/限额约束，且有回滚方案与监控 |
| **禁止发布** | 存在未缓解的 P0；或关键不变量为 GAP 且无补偿控制 |
| **证据不足，无法判定** | 关键路径的结论停留在 NOT_VERIFIED，且无法在发布前取得证据 |

**"证据不足"是一个合法且必须敢于使用的结论。** 把它硬说成"允许发布"，就是在用发布决策掩盖评审失败。

```
  <具体方案；若有多种，说明取舍>

修复后的回归要求
  <必须新增/修改哪些测试；验收标准>
```

### 9.2 报告的必填项

1. **结论摘要表**：编号 / 级别 / 主题 / 证据状态
2. **已验证通过的控制**：必须给证据，不能只写结论
3. **被否定的候选问题**：诚实记录自己的误判——这能防止后续评审重复踩坑
4. **仍未验证的假设**：每条附验证方案与阻塞条件
5. **明确的未覆盖范围**
6. **复现命令清单**

### 9.3 禁止事项

- 禁止用评分代替结论
- 禁止把"没发现问题"写成"验证通过"
- 禁止省略"未覆盖范围"
- 禁止在证据不足时给出"基本没问题"这类模糊结论

## 10. 长期机制：把评审变成可追踪的关系

单次评审的价值有限，真正的收益来自把下面五者建立可追踪关系：

```
需求 → 不变量 → 实现 → 测试证据 → 发布门禁
```

落地的具体形态：

| 机制 | 形态 | 作用 |
| --- | --- | --- |
| 不变量登记表 | `02-invariants.md` 的 INV-xx，每条带强制机制层级与状态 | 让"必须永远为真的事"有唯一清单 |
| 发现编号 | `PREFIX-NN`（如 ORD-001、SEC-003）贯穿报告、PR、测试 | 让问题能跨轮次追踪，不重复发现 |
| 回归测试绑定 | 每条 P0/P1 修复必须新增测试，测试名或注释引用发现编号 | 让修复可验证，让不变量有持续看护 |
| 证据状态回填 | 每轮评审回填上一轮的 NOT_VERIFIED | 让"未验证"不会永远悬空 |
| 发布门禁 | §8 的四态结论 + P0 归零作为硬门 | 让评审结论真的能拦发布 |

**评审的产出不应该只是一份报告，而应该是一组能被下一轮直接复用的状态。**
