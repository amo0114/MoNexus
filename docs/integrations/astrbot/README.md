# MoNexus 签到机器人（AstrBot 插件）

把每日签到从「必须打开网站」搬到 QQ。绑定一次后，用户在群聊或私聊里发「签到」即可领积分，机器人还会每天定点私聊提醒当天没签到的人。

## 能力

| 命令 | 场景 | 说明 |
| --- | --- | --- |
| `/绑定 <邮箱>` | 群 / 私聊 | 向注册邮箱发送 6 位验证码（无需打开网站） |
| `/确认 <验证码>` | 群 / 私聊 | 校验验证码并完成绑定 |
| `签到` / `打卡` | 群 / 私聊 | 领取当日积分，群聊默认需 @机器人 |
| `我的积分` | 群 / 私聊 | 查余额、会员等级、今日签到状态 |
| `/解绑` | 群 / 私聊 | 解除绑定 |
| — | 自动 | 每天定点私聊今日未签到的已绑定用户 |

## 部署

### 1. 服务端

在 `.env` 里加共享密钥（务必高熵）：

```bash
openssl rand -hex 32   # 生成一个
# 写入 .env：
BOT_SHARED_SECRET=<上面生成的 64 位十六进制>
BOT_REMINDER_ENABLED=true
```

重启后端。验证通道已开：

```bash
curl -i -X POST http://<你的域名>/api/bot/checkin \
  -H 'Content-Type: application/json' -d '{}'
# 期望 401 BOT_UNAUTHORIZED（说明通道已启用且在验签）
# 若返回 503 BOT_NOT_CONFIGURED，说明密钥没生效
```

### 2. AstrBot 插件

把 `monexus_checkin/` 整个目录放进 AstrBot 的 `data/plugins/` 下，重启或在面板重载插件，然后在插件配置里填：

| 字段 | 值 |
| --- | --- |
| `api_base` | `https://<你的域名>`（**不要**带 `/api`） |
| `bot_secret` | 与 `BOT_SHARED_SECRET` 完全一致 |
| `platform` | `qq` |
| `reminder_hour` / `reminder_minute` | 催签时间，默认 21:00 |

### 3. 用户绑定

1. 在群里发 `/绑定 you@example.com`（填**注册邮箱**）
2. 邮箱收到 6 位验证码，回群里发 `/确认 123456`
3. 绑定完成，之后随时发「签到」

全程不离开 QQ —— 这是刻意设计：让用户为签到而打开网站，等于用「来网站」解决「不来网站」的问题。

## 设计要点

**为什么用 HMAC 而不是给机器人发 JWT。** 机器人是长期在线服务，持长效 JWT 等于揣着一把能开全站任何门的钥匙，一旦泄露后果是全域的。HMAC 方案把机器人的权限面收敛到 `/api/bot/*` 这一小组接口，且签名带时间戳，泄露的签名只在 5 分钟窗口内、且只对单个接口有效。

**签名算法**（两端必须逐字节一致）：

```
1. 取请求体所有字段 + timestamp + _path
2. 丢掉 sign 自身与 null 值
3. 按 key 字典序拼成 k1=v1&k2=v2（值不做 URL 编码）
4. HMAC-SHA256(payload, secret) → 小写 hex
```

`_path` 参与签名是关键：否则抓到一个合法签名就能把它挪用到另一个 bot 接口上。

**邮箱为什么能当身份锚点。** 签到接口强制 `requireVerifiedEmail`，所以能签到的人，邮箱必然已通过验证。邮箱是注册时用户亲自填并经邮件验证的，是一条既成的信任链 —— 比让用户回网站抄一个绑定码更强，也更省事。

**验证码必须限次。** 6 位数字只有 10^6 空间，不限次可被枚举。实现上用 `failedAttempts` 计数，上限 5 次，触顶即把该行作废。这里有一个**必须避开的陷阱**：Prisma 交互式事务只要回调抛异常就整体回滚，包括失败计数那次 `update`。若在事务内直接 `throw`，计数会被回滚，限次形同虚设。因此 `confirmBind` 的事务内只做判定并**返回**结论，待事务提交、计数落库后，再把结论翻译成 HTTP 错误。这条约束在代码里以注释显式标注，改动时不要破坏。

**验证码只存哈希。** 库里存 `sha256(code)`，即便数据库被读取也无法反推出可用验证码。

**发码接口不做账号枚举。** `/bind/request` 对「邮箱不存在/未验证/被封禁」一律返回同一句成功响应，但不会真的发信。否则这个接口就成了批量探测「哪些邮箱注册过」的工具。

**身份不由请求体决定。** `/api/bot/*` 的请求体里**没有** `userId` —— 后端用 `platformId` 反查绑定表。若允许客户端传 `userId`，等于给机器人开了任意用户冒用通道。

**签到幂等复用同一把锁。** 机器人签到走的是与网页完全相同的 `CheckinRecord @@unique([userId, date])`，只是多记一个 `source` 字段做统计。所以「网页签过、QQ 再签」会被正确拒绝，不会双倍发分。

**QQ 号必须当字符串。** 18 位以上的 QQ 号超出 JS/Python 的数字安全范围，一旦被解析成数字再拿去签名，必然与后端对不上。插件里所有 `platformId` 都是 `str()` 处理，数据库侧也是 `TEXT`。

## 排障

| 现象 | 原因 |
| --- | --- |
| `503 BOT_NOT_CONFIGURED` | 服务端没读到 `BOT_SHARED_SECRET`，检查是否重启 |
| `401 签名校验失败` | 两端密钥不一致，或 `api_base` 多了 `/api` |
| `401 请求已过期` | 机器人服务器时钟偏移超过 5 分钟，校准 NTP |
| 验证码无效/过期 | 10 分钟过期，需重新发 `/绑定 <邮箱>` |
| 提示"尝试次数过多" | 错误码连续 5 次即作废，重新发 `/绑定 <邮箱>` |
| 发码后收不到邮件 | 确认邮箱是注册邮箱且已验证；未注册邮箱会被静默忽略 |
| 群里发签到没反应 | 默认需 @机器人（`group_at_required: true`） |
| 催签没发出去 | QQ 对主动私聊有风控；确认用户已加机器人好友 |

## 已验证行为

服务端 e2e（真实 HTTP + 真实数据库）覆盖：未绑定签到降级为提示、发码、验证码哈希反查正确、错误码计数 1→5 持久化、第 5 次触顶作废、第 6 次返回 404、正确码绑定成功、重复 `/确认` 幂等不重复建记录、首次签到 +50、重复签到返回已签、查询余额等级、催签名单正反两向、解绑后降级、未注册邮箱不泄露账号状态、签名错误 401、时间戳过期 401、签名跨接口挪用 401。18 位 QQ 号精度完好。

Python 侧与 Node 侧的签名算法用同一组输入做过向量比对，输出逐字节一致。
